## 一、方案概述

### 1.1 建设目标

本方案围绕两个核心能力展开：  

| 能力               | 说明                                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| **子应用激活与授权状态汇聚** | 子应用首次启动时携带 `appCode + machineCode` 向集成平台申请本机 Licence 并完成激活；平台登记激活结果，并在撤销、续期或模块暂停时通过 SSE 主动通知子应用；平台统一展示每个子应用的授权状态 |
| **模块级授权控制**      | 一份子应用 Licence 可以包含多个业务模块，每个模块可独立配置有效期；未授权模块由子应用在服务端拦截                                                            |

子应用运行期使用三份 Licence 数据：启动时优先读取集成平台，失败时读取本地文件；启动成功后把 Licence 信息载入内存缓存；后续接口拦截只读取内存缓存，不访问平台或本地文件。运行期授权判定由子应用在本地完成，不依赖心跳。

### 1.3 设计原则

1. **LicenceData 由脚本签名生成**：签名私钥只在生成脚本/离线签名环境中保存；平台和子应用只持有公钥。  
2. **appCode 是子应用唯一标识**：子应用本身就是一个租户，不再引入额外租户字段。  
3. **一机一 Licence**：`machineCode` 是实例唯一标识；每份 Licence 只绑定一台机器、只允许该机器激活。多台机器部署时分别签发 Licence。  
4. **模块只控制授权与有效期**：模块不设置任何数量配额。  
5. **平台负责登记、激活、撤销和审计**：平台是授权管理控制中心，不承担子应用运行期请求拦截；授权状态变更通过通知下发，运行期由子应用判定。  
6. **客户端能力由子应用自行实现**：本地验签、首次激活、本地文件读写、内存缓存、启动联网查询、状态通知处理和模块拦截由各子应用按本文协议实现。  
7. **签名数据是授权边界**：平台可以撤销 Licence、下发续期 Licence 或暂停已授权模块，但不能增加签名 LicenceData 之外的模块，也不能延长签名有效期。  
8. **无心跳**：运行期授权由子应用在本地判定；启动时优先联网查询平台状态，网络不可用时使用本地文件，启动成功后载入内存缓存。  
9. **三份 Licence 数据职责清晰**：平台用于启动查询和激活；本地 `licence.txt` 用于持久化和离线兜底；内存缓存用于运行期接口拦截。启动成功后统一载入内存，收到平台通知时同步更新内存缓存和本地文件。  
10. **三份数据都不是信任根**：平台数据、本地文件和内存缓存都必须来自验签通过的 LicenceData 或平台签名通知；验签失败或数据损坏时按无授权处理。  
11. **请求身份是二元组**：子应用对平台的每次 Licence 请求（授权信息获取、激活、启动状态查询、建立 SSE 连接、通知确认）都必须同时携带 `appCode` 和 `machineCode`；平台以 `(appCode, machineCode)` 定位唯一有效 Licence，不接受只带 `appCode` 或只带 `machineCode` 的请求。  
12. **通知通道使用 SSE**：平台通过 SSE 单向推送撤销/续期/模块暂停通知，子应用通过独立 HTTPS 接口回传确认；不引入消息队列，也不使用 WebSocket。
13. **HA/灾备初验预激活与授权节点池**：针对主备 HA 及异地灾备节点，在初验上线阶段统一启动连网集成平台完成一次首次激活，确保备机本地持久化生成合法 `licence.txt`，保证灾备接管时可直接离线启动；K8s 规划多节点授权池支持 Pod 故障漂移自愈；在商业履约上随附灾备许可不重复计收软件许可费。
14. **免重启按需状态对齐**：在不支持 SSE 或 SSE 长连接受阻的网络环境下，支持在子应用管理端“手动同步授权状态”，按需调用 HTTPS `/status` 短连接接口完成热对齐，无需重启业务进程。  

### 1.4 范围与边界

- 本文包含：LicenceData 模型、生成脚本扩展、平台功能、子应用需要实现的工作、交互协议、本地 Licence 文件、内存缓存以及撤销/续期通知。  
- 本文不包含：子应用具体技术栈实现细节。  
- 本方案不包含心跳机制，也不包含用户数限制。  

### 1.5 方案选择说明

本方案采用“平台在线激活 + 本地 Licence 文件 + 内存缓存 + 平台撤销/续期通知”的模式，原因：  

- 子应用本身已接入集成平台，平台可用性已由现有体系保障；  
- 首次激活必须联网，确保机器码、Licence 登记和激活状态由平台确认；  
- 后续启动优先联网查询平台状态，仅网络不可用时使用本地文件，避免平台短暂故障导致子应用批量无法启动；  
- 平台可以统一管理 Licence 的登记、激活、续期、撤销和审计；  
- 一机一 Licence，可以精确识别超范围部署，并通过平台撤销；  
- 无心跳降低了子应用的运行期依赖和实现成本，撤销以及续期状态通过平台通知下发，未送达时由平台展示执行失败；  
- 运行期接口拦截只读内存缓存，避免每次请求都访问平台或本地文件；启动成功后统一把 Licence 信息载入内存；  
- 模块授权状态可以在平台集中展示和治理。

## 二、核心概念

| 概念            | 说明                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------- |
| 子应用           | 一个独立的业务应用，本身就是一个租户                                                                       |
| `appCode`     | 子应用唯一标识；平台和脚本均以它识别子应用                                                                    |
| `machineCode` | 机器码，作为实例唯一标识；一份 Licence 只绑定一台机器                                                          |
| LicenceData   | 由脚本生成的 JSON 文本，粘贴/上传到平台登记；首次激活时以授权码形式下发给子应用                                              |
| 授权码           | 由 LicenceData 编码得到的字符串，首次激活时由平台下发，子应用用于本地验签并写入本地文件                                       |
| `licenceId`   | Licence 唯一编号，用于平台登记、激活和审计                                                                |
| `moduleCode`  | 模块编码，如 `performance.report`                                                              |
| 首次激活          | 子应用第一次启动时向平台获取本机授权信息（授权码、公钥等），本地验签后调用激活接口                                                |
| 启动状态查询        | 已有本地 Licence 的子应用每次启动且网络可用时，向平台查询本机 Licence 的最新状态                                        |
| 状态通知          | 平台撤销 Licence、下发续期 Licence 或暂停/恢复模块时，通过 SSE 通道主动推送；子应用同时更新内存缓存和本地文件                       |
| 通知确认          | SSE 为单向通道，子应用处理完通知后通过独立 HTTPS 接口回传 `noticeId`、`memoryUpdated`、`fileUpdated`；平台据此判定通知是否完成 |
| 本地 Licence 文件 | 子应用激活成功后生成的 `licence.txt`，保存授权码、公钥、状态和通知信息，用于持久化和离线启动                                    |
| 内存 Licence 缓存 | 启动成功后由平台结果或本地文件载入内存的 Licence 状态；运行期接口拦截只读该缓存                                             |
| 授权成功          | 本地验签通过，且平台返回已激活/有效；或启动时网络不可达但本地文件有效且未撤销；启动成功后载入内存缓存                                      |
| 授权失败          | 本地验签失败、机器码不匹配、未激活、已撤销、已过期、无有效本地文件或内存缓存等                                                  |

### 2.1 标识规则

| 对象      | 唯一标识          | 说明                                               |
| ------- | ------------- | ------------------------------------------------ |
| 子应用     | `appCode`     | 全局唯一，如 `performance`、`rad-screen`；由子应用已有平台接入配置提供 |
| 实例      | `machineCode` | 同一 appCode 下唯一                                   |
| Licence | `licenceId`   | 脚本生成；同一时刻与 `(appCode, machineCode)` 一一对应         |
| 模块      | `moduleCode`  | 建议为 `appCode.module`                             |

平台侧唯一键：  

```text
(appCode, machineCode)  
```

约束：  

- 同一 `(appCode, machineCode)` 同时只能存在一份有效 Licence；  
- 续期或重新签发时，新 Licence 使用更高的 `revision` 替代旧 Licence；  
- 机器码变更视为新实例，必须重新申请 Licence，不能沿用旧 Licence。  
- `appCode` 由子应用已有的平台接入配置提供；首次激活前尚未获得 Licence，不能从 Licence 中解析。  
- **每次请求都必须同时携带 `appCode` 和 `machineCode`**：`appCode` 只标识应用，同一应用多机部署时无法定位实例；平台以 `(appCode, machineCode)` 为唯一键拉取该实例的一份有效 Licence。`licenceId` 可用于校验和审计，但不能替代该组合键。  
- `machineCode` 不是秘密，可放在请求头或 SSE 查询参数中；平台必须校验它与请求凭据绑定的 `appCode` 匹配，防止越权读取其他应用的 Licence。  
- `machineCode` 去除首尾空白后按原样比较（区分大小写），长度不超过 64，字符集限定为 `A-Z a-z 0-9 - _ .`；子应用与平台使用同一规范化规则。  
- 机器码统一按第八章规则生成：对选定硬件特征添加来源前缀后计算 SHA-256，取 64 位小写十六进制作为 `machineCode`；该形式满足本条长度和字符集约束，并按原样（区分大小写）比较；哈希规则一经使用必须保持稳定，并在 Licence 签发、激活、查询和 SSE 建连中保持一致。

## 三、LicenceData 与生成脚本

### 3.1 LicenceData 是什么

**LicenceData 是生成脚本的输出物，不是生成命令的输入参数。**  

生成命令的输入是：appCode、machineCode、有效期、授权类型、模块列表等业务参数。  

生成命令输出：  

1. `licence.json`（LicenceData）：粘贴/上传到集成平台 License 管理页面；  
2. 可选的可读摘要，仅用于管理员核对，不参与子应用运行。  

部署人员只需要把 `licence.json` 导入平台，无需在启动参数中传授权码。后续流程为：  

```text
KeyGen 生成 licence.json  ↓平台导入、验签、登记并绑定机器码  
  ↓子应用首次启动 → 携带 appCode + machineCode 向平台获取本机授权码和公钥 → 本地验签 → 调用激活接口  
  ↓子应用激活成功后生成本地 licence.txt，并载入内存缓存  
  ↓后续重启：携带 appCode + machineCode 优先联网查询平台状态；网络不可用时读取 licence.txt  ↓运行期接口拦截只读内存缓存  
```

子应用本地生成的 `licence.txt` 与 KeyGen 输出是两种不同文件：  

- KeyGen 输出 `licence.json`，是平台登记的原始签名数据；  
- 子应用输出 `licence.txt`，是本地持久化文件，包含授权码、公钥、状态和通知信息。  

授权码定义为 `Base64(UTF-8(LicenceData JSON 原文))`。平台下发、子应用验签、本地文件和内存缓存均使用同一编码，避免不同语言对字符集和换行的处理差异。  

部署人员只有 jar 包时，可使用的启动参数：  

- `--licence-cache`：本地 Licence 文件路径，可选，默认 `./licence.txt`；  
- `--licence-public-key`：可选，用于固定 Licence 公钥；不配置时使用平台下发公钥；如果配置，平台下发的公钥必须与之一致；  
- `--licence-enable`：可选，设为 `false` 仅用于开发调试。  

集成平台地址和鉴权凭据复用子应用已有的平台接入配置，不在 Licence 启动参数中重复配置。`appCode` 也复用已有平台接入配置。公钥不是秘密，但固定公钥可以降低平台被攻破后同时伪造公钥和授权的风险。  

### 3.2 LicenceData JSON 结构

```json
{  
  "formatVersion": 1,  "revision": 1,  "licenceId": "LIC-20261022-0001",  "supersedesLicenceId": null,  "appCode": "performance",  "appName": "绩效系统",  
  "machineCode": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",  "validFrom": "2026-01-01",  "expiryDate": "2027-12-31",  "licenceType": "ENTERPRISE",  "message": "授权已过期，请联系系统管理员",  
  "modules": [    {      "code": "performance.core",      "name": "绩效管理",  
      "validFrom": "2026-01-01",      "expiryDate": "2027-12-31"    },    {      "code": "performance.report",      "name": "绩效报表",  
      "validFrom": "2026-01-01",      "expiryDate": "2027-12-31"    }  ],  "issuedAt": "2026-10-22T17:06:22+08:00",  "keyId": "licence-key-2026",  "sigAlg": "RSASSA-PSS-SHA256",  "checksum": "<SHA256>",  "signature": "<RSA 签名 Base64>"}  
```

> 说明：示例中的 `machineCode` 固定为 64 位小写 SHA-256 十六进制字符串（此处仅为示例值）；实际取值由子应用按第八章规则计算，平台与子应用均按 2.1 的长度和字符集校验。  

字段说明：  

| 字段                    | 必填  | 说明                                         |
| --------------------- | --- | ------------------------------------------ |
| `formatVersion`       | 是   | 格式版本，当前为 1                                 |
| `revision`            | 是   | Licence 版本号，单调递增；续期或重新签发时必须大于被替代版本         |
| `licenceId`           | 是   | Licence 唯一编号                               |
| `supersedesLicenceId` | 否   | 被本 Licence 替代的旧 `licenceId`；首次签发为空         |
| `appCode`             | 是   | 子应用唯一标识                                    |
| `appName`             | 否   | 子应用显示名称                                    |
| `machineCode`         | 是   | 目标机器码；一份 Licence 只允许该机器激活                  |
| `validFrom`           | 是   | 生效日期 `yyyy-MM-dd`                          |
| `expiryDate`          | 是   | 到期日期 `yyyy-MM-dd`                          |
| `licenceType`         | 是   | `STANDARD` / `PROFESSIONAL` / `ENTERPRISE` |
| `message`             | 否   | 到期提示                                       |
| `modules`             | 是   | 模块列表；空数组表示无业务模块                            |
| `module.code`         | 是   | 模块编码                                       |
| `module.name`         | 否   | 模块显示名称                                     |
| `module.validFrom`    | 否   | 为空时继承应用级                                   |
| `module.expiryDate`   | 否   | 为空时继承应用级                                   |
| `issuedAt`            | 是   | 签发时间，ISO-8601                              |
| `keyId`               | 是   | 签名密钥标识；平台据此选择验签公钥                          |
| `sigAlg`              | 是   | 签名算法，当前为 `RSASSA-PSS-SHA256`               |
| `checksum`            | 是   | 规范化数据校验和                                   |
| `signature`           | 是   | 签名，Base64                                  |

模块不包含任何配额字段。  

### 3.3 生成命令扩展

> 本节参数是 Licence 生成脚本（KeyGen）的参数，不是子应用启动参数。  

| 参数                | 必填  | 说明                                                                    |
| ----------------- | --- | --------------------------------------------------------------------- |
| `--mode=cli`      | 否   | 命令行模式                                                                 |
| `--app-code`      | 是   | 子应用唯一标识                                                               |
| `--machine-code`  | 是   | 目标机器码；一机一 Licence，每台机器单独签发                                            |
| `--valid-from`    | 是   | 生效日期 `yyyy-MM-dd`                                                     |
| `--expiry`        | 是   | 到期日期 `yyyy-MM-dd`                                                     |
| `--type`          | 否   | `STANDARD` / `PROFESSIONAL` / `ENTERPRISE`，默认 `PROFESSIONAL`          |
| `--modules-file`  | 否   | 模块 JSON 文件，包含 `code`、`name`、`validFrom`、`expiryDate`；模块展示名和有效期都以此文件为准 |
| `--message`       | 否   | 到期提示                                                                  |
| `--output-format` | 否   | `json`（默认，供平台导入）/ `text`（可读摘要）                                        |
| `--output`        | 否   | 输出文件路径；默认控制台输出                                                        |
| `--licence-id`    | 否   | 指定 Licence 编号；不填则自动生成                                                 |
| `--revision`      | 否   | 指定版本号；首次签发不填时默认 1，续期时必须显式填写大于被替代版本的数值                                 |
| `--supersedes`    | 否   | 被替代的旧 `licenceId`；续期时填写                                               |
| `--key-id`        | 否   | 指定签名密钥标识；用于密钥轮换                                                       |
| `--help`          | 否   | 显示帮助                                                                  |

> 注意：命令参数中没有 `--licence-data`。LicenceData 是脚本执行后生成的输出文本，不是命令的输入参数。  

`modules.json` 示例：  

```json
[  
  {    "code": "performance.core",    "name": "绩效管理",  
    "validFrom": "2026-01-01",    "expiryDate": "2027-12-31"  },  {    "code": "performance.report",    "name": "绩效报表",  
    "validFrom": "2026-01-01",    "expiryDate": "2027-06-30"  },  {    "code": "performance.analysis",    "name": "绩效分析",  
    "validFrom": "2026-06-01",    "expiryDate": "2027-12-31"  }]  
```

生成命令：  

```bash
java -jar keygen.jar --mode=cli \  --app-code=performance \  --machine-code=9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08 \  --valid-from=2026-01-01 \  --expiry=2027-12-31 \  --type=ENTERPRISE \  --modules-file=modules.json \  --message="授权已过期，请联系系统管理员" \  
  --revision=1 \  --key-id=licence-key-2026 \  --output-format=json \  --output=licence.json```  

生成结果：  

```text  
licence.json    ← LicenceData JSON，导入集成平台  
licence-summary.txt  ← 可选，管理员核对用可读摘要  
```

补充说明：  

- `modules.json` 是模块展示名、有效期的唯一来源，不再维护全局模块目录；  
- 需要授权模块时，必须通过 `--modules-file` 提供 `modules.json`；  
- `modules.json` 中的 `code` 在同一份文件中必须唯一，`name` 必填；  
- 模块的 `validFrom` / `expiryDate` 可以省略，省略时继承应用级；  
- 模块生效日期不得早于应用级 `validFrom`；  
- 模块到期日期不得晚于应用级 `expiryDate`；  
- 任一模块超出应用级有效期时，脚本直接报错，不生成 LicenceData；  
- 脚本在生成时按 `code` 排序模块、计算 checksum、执行签名；  
- `licence.json` 是平台导入的**唯一标准格式**；  
- 续期或重新签发时，管理员应先在平台查看当前有效 Licence 的 `revision`，并使用更大的 `--revision`；平台拒绝不递增的版本导入；  
- KeyGen 不再生成子应用本地 Licence 文件 `licence.txt`，避免与子应用生成的本地文件混淆。  

### 3.4 校验和与签名

为保证多语言实现一致，LicenceData 的规范化、校验和与签名规则如下：  

1. 移除 `checksum` 和 `signature` 字段；  
2. 将 `modules` 数组按 `code` 升序排序；  
3. 使用 RFC 8785（JSON Canonicalization Scheme, JCS）序列化为 UTF-8 字节；JCS 负责 key 排序、字符串转义、数字格式和空白处理；  
4. `checksum = SHA256(规范化字节)`，输出小写十六进制；  
5. `signature = RSASSA-PSS(SHA-256, MGF1-SHA-256, saltLength=32)(规范化字节)`，输出 Base64；  
6. 平台和子应用验签时按同样步骤重新规范化、计算 checksum，并使用 `keyId` 对应公钥验证签名。  

签名参数固定为：  

| 项       | 规定                            |
| ------- | ----------------------------- |
| 规范化     | RFC 8785 JCS，UTF-8，无多余空白      |
| 签名算法    | RSASSA-PSS + SHA-256          |
| MGF     | MGF1 + SHA-256                |
| Salt 长度 | 32 字节                         |
| 密钥长度    | RSA 2048 位及以上，推荐 3072 位       |
| 编码      | Base64                        |
| 密钥标识    | `keyId`，随 LicenceData 和平台响应携带 |

密钥轮换：  

- 平台维护公钥版本表，按 `keyId` 选择验签公钥；  
- 新旧密钥保留重叠有效期，旧 Licence 在到期前必须仍可验签；  
- 平台下发授权信息时返回与 LicenceData `keyId` 匹配的公钥；  
- 子应用在本地文件和内存缓存中保存 `keyId` 和对应公钥，离线启动时按 `keyId` 验签。  

平台响应和撤销/续期通知使用**独立于 Licence 签名的平台密钥**；平台密钥同样支持 `keyId` 和轮换。平台响应应包含 `timestamp`、`nonce`、`requestId` 并签名，子应用校验时间窗和 nonce 防止重放。  

建议提供一组跨语言测试向量（固定 LicenceData、期望规范化字节、checksum、signature），作为 Java/Go/Python 等实现的一致性验收项。  

### 3.5 modules.json 规范

本方案不维护全局模块目录。每次签发时，由部署人员与客户约定本次启用的模块，把模块信息直接写入 `modules.json`，脚本以该文件为准生成 LicenceData。  

`modules.json` 字段：  

| 字段           | 必填  | 说明                           |
| ------------ | --- | ---------------------------- |
| `code`       | 是   | 模块编码，同一文件中唯一                 |
| `name`       | 是   | 模块展示名，平台和页面直接使用该名称           |
| `validFrom`  | 否   | 模块生效日期；为空时继承应用级 `validFrom`  |
| `expiryDate` | 否   | 模块到期日期；为空时继承应用级 `expiryDate` |

规则：  

- `modules.json` 是本次 Licence 的模块清单，不是全局目录；  
- 模块展示名以 `name` 为准，不再从其他全局目录查询；  
- 始终启用的基础功能不需要列入 `modules.json`，但子应用仍须在拦截器中显式声明为基础模块，不能在 fail-closed 下默认放行；  
- 模块编码由子应用研发提供并保持稳定，编码一经签发不得变更；  
- 脚本不校验模块编码是否在外部目录中存在，只做格式、唯一性、日期范围和签名校验。  

示例：  

```json
[  
  {    "code": "performance.core",    "name": "绩效管理",  
    "validFrom": "2026-01-01",    "expiryDate": "2027-12-31"  },  {    "code": "performance.report",    "name": "绩效报表",  
    "validFrom": "2026-01-01",    "expiryDate": "2027-06-30"  }]  
```

### 3.6 与现有 `docs/licence.txt` 的关系

现有 `docs/licence.txt` 是旧脚本导出的可读授权文件，包含 Base64 授权码、RSA 公钥、机器码、有效期、授权类型、时间戳和 checksum。  

在新方案中：  

- 继续沿用同一对 RSA 密钥体系；密钥轮换后按 `keyId` 区分；  
- KeyGen 改为输出标准 `licence.json`（LicenceData），供平台导入；  
- 子应用激活成功后自行生成 `licence.txt` 本地 Licence 文件；该文件由子应用维护，KeyGen 不再生成；  
- 平台下发的公钥可用于平台和子应用验签；  
- 如果私钥文件曾经出现在代码库、文档目录或交付包中，应按泄露处理并轮换密钥。

## 四、集成平台功能设计

### 4.1 License 管理

平台提供 License 管理页面，支持：  

| 功能                | 说明                                                            |
| ----------------- | ------------------------------------------------------------- |
| 粘贴/上传 LicenceData | 接受 `licence.json` 文本或文件                                       |
| 验签                | 使用 `keyId` 对应公钥验证 checksum 和 RSA 签名                           |
| 登记                | 保存 LicenceData、appCode、machineCode、licenceId、revision、有效期、模块  |
| 绑定机器码             | 校验 LicenceData 中的 machineCode 与部署机器一致，一机一 Licence             |
| 下发授权信息            | 首次激活时返回本机授权码、公钥、keyId、有效期和模块                                  |
| 激活                | 标记该 Licence 在该机器码上已激活                                         |
| 提供最新授权状态          | 启动状态查询时返回激活、撤销、模块暂停、剩余天数；如有更新版 LicenceData 一并返回，由子应用再次验签      |
| 撤销                | 撤销某份 Licence，并向子应用发送撤销通知                                      |
| 续期                | 生成 `revision` 更高的新 LicenceData 后重新导入，替代旧版本，并向子应用发送续期通知        |
| 展示通知结果            | 记录撤销/续期/模块暂停通知的发送、子应用确认以及内存缓存和本地文件更新结果；未确认或失败时在页面展示执行失败，并支持重试 |
| 审计                | 记录导入、激活、撤销、续期、模块暂停、通知确认等操作                                    |

平台保存 LicenceData 的原始 JSON 字节，不做重新序列化，避免破坏签名。  

### 4.2 授权信息获取与首次激活

首次激活必须联网，流程如下：  

```text
子应用首次启动  
  ↓调用“授权信息获取”接口：携带 appCode + machineCode 和平台身份  
  ↓平台校验：  
  - 该 (appCode, machineCode) 已登记 Licence  - Licence 未过期、未撤销  
  - 机器码匹配；同一机器重复激活按幂等处理  
  ↓平台返回：授权码（LicenceData）、Licence 公钥、平台通知验签公钥、keyId、licenceId、revision、有效期、模块  
  ↓子应用本地验签并校验 appCode / machineCode / 有效期 / 模块  
  ↓调用“激活”接口，平台标记已激活并返回激活结果  
  ↓子应用生成本地 licence.txt，并载入内存缓存，启动成功  
```

规则：  

- 首次激活必须在线，平台不可达时启动失败；  
- 授权信息获取和激活请求都必须同时携带 `appCode` 和 `machineCode`；平台以 `(appCode, machineCode)` 定位唯一有效 Licence，缺少任一项或与凭据绑定的应用不一致时直接拒绝；  
- 未登记、机器码不匹配、已撤销、已过期时，授权信息获取或激活失败；  
- 激活接口必须幂等，重复调用返回同一激活结果；  
- 子应用在调用激活接口前必须完成本地验签；  
- 子应用默认从平台响应获取 Licence 公钥进行验签；若配置了 `--licence-public-key`，平台下发的公钥必须与固定公钥一致，否则拒绝激活；  
- 激活成功后，子应用把授权码、Licence 公钥、平台通知验签公钥、keyId、licenceId、revision、有效期、状态写入本地 `licence.txt`，并载入内存缓存。  

### 4.3 启动状态查询

适用于已有本地 Licence 的重启场景。子应用每次启动且网络可用时，调用启动状态查询接口：  

- 必须携带 `appCode + machineCode`，并附带本地 `licenceId` 和 `revision`；平台以 `(appCode, machineCode)` 定位该实例的唯一有效 Licence，`licenceId` 只用于一致性校验；  
- 平台返回当前授权状态：已激活、已撤销、模块暂停、已过期、剩余天数；  
- 如果平台存在 `revision` 更高的 LicenceData（续期或其他更新），返回最新授权码和公钥，由子应用验签后同时替换本地文件和内存缓存；  
- 平台返回的 `revision` 低于本地记录时，视为异常，保留本地版本并告警，不得回退；  
- 平台状态是联网启动时的权威状态；返回已撤销时，子应用同时更新本地文件和内存缓存并阻断启动；  
- 只有网络错误、超时或平台不可用（连接失败、5xx）才允许降级读取本地 `licence.txt`；  
- 平台明确返回未登记、未激活、已撤销、已过期等业务错误时，必须按授权失败处理，不能降级到本地文件；  
- 启动成功后，最终选定的 Licence 信息必须载入内存缓存，供运行期接口拦截使用；  
- 无有效本地文件时启动失败。  

本接口只在启动时调用，不承担心跳职责。  

### 4.4 撤销、续期与暂停通知（SSE）

平台撤销 Licence、下发续期 Licence 或暂停/恢复模块时，通过 **SSE（Server-Sent Events）** 单向推送通知，子应用处理完成后通过独立 HTTPS 接口回传确认。本方案不引入消息队列，也不使用 WebSocket。  

选择 SSE 的原因：  

- 基于普通 HTTP/HTTPS，复用现有网关、鉴权、TLS 和日志体系，不需要新增 MQ 中间件及其网络开通和运维；  
- 本场景只需要平台到子应用的单向推送，SSE 的能力刚好匹配；  
- SSE 自带事件 `id`、断线重连和 `Last-Event-ID` 续传语义，客户端实现简单；  
- 子应用确认走普通 HTTPS POST，不需要维持双向长连接。  

通知内容至少包含：  

- `noticeId`：通知唯一编号，用于 SSE 事件 `id`、幂等和确认；  
- `action`：`REVOKE` / `RENEW` / `SUSPEND_MODULE` / `RESUME_MODULE`；  
- `licenceId`、`appCode`、`machineCode`；`appCode + machineCode` 必须与 SSE 连接携带的实例身份一致；  
- `revision`：通知对应的 Licence 版本；`RENEW` 时为新的 revision；  
- `licenceCode`、`licencePublicKey`、`licenceKeyId`：`RENEW` 时必填，携带新的已签名 LicenceData 和公钥；  
- `supersedesLicenceId`：`RENEW` 时可选，标识被替代的旧 Licence；  
- `moduleCode`：模块暂停/恢复时必填；  
- `issuedAt`、`nonce`、`reason`；  
- `platformKeyId` 和平台签名。  

子应用处理流程：  

```text
SSE 收到 licence-notice 事件  
  ↓校验平台签名、platformKeyId、时间窗、nonce、machineCode、licenceId 和 action  ├─ RENEW：额外验签新 LicenceData，校验 appCode、machineCode 和 revision 递增  
  └─ 其他：按当前 Licence 校验  
  ↓按 noticeId 幂等检查（已处理过的通知直接返回上次确认结果）  
  ↓同时更新内存缓存和本地 licence.txt  ├─ REVOKE：先更新内存为 REVOKED（立即阻断），再原子改写本地文件  
  ├─ RENEW：先原子写入新 Licence 到本地文件，成功后再切换内存缓存  
  └─ SUSPEND/RESUME：先更新内存模块状态（立即生效），再原子改写本地文件  
  ↓通过 HTTPS 确认接口返回（noticeId、action、revision、memoryUpdated、fileUpdated、appliedAt）  
  ├─ 内存和本地文件均更新成功 → 执行成功  
  └─ 任一失败 → 返回失败结果和原因  
  ↓平台记录确认结果  
```

平台侧规则：  

- 只有收到子应用成功确认（`memoryUpdated=true` 且 `fileUpdated=true`），才把通知状态记为完成；  
- SSE 连接未建立、通知未送达、子应用未确认、内存更新失败、本地写入失败或确认超时（默认 30 秒）时，平台在页面展示执行失败，并按退避策略重发同一 `noticeId`；  
- SSE 连接断开后，平台保留该实例未确认的通知（默认 7 天）；子应用重连时按 `Last-Event-ID` 补发；超出保留期或无法续传时发送 `replay-required`，由子应用调用启动状态查询接口对齐；  
- 撤销通知失败时，若子应用内存已切换为撤销状态，运行期应立即阻断，但平台仍展示“撤销失败”，直到本地文件补写成功；  
- 续期通知失败时，子应用保留并使用旧 Licence；旧 Licence 已过期则按过期状态阻断业务；平台展示“续期失败”并重试；  
- 子应用下次联网启动查询时，平台再次返回最新撤销/续期状态，完成补偿；  
- 通知和确认都必须幂等，重复通知不得造成状态回退；  
- 平台多实例部署时，由平台内部把通知投递到持有该 `(appCode, machineCode)` SSE 连接的实例；这是平台实现细节，客户端协议不变。  

SSE 连接、事件格式、重连与确认报文见 6.3 和 6.4。  

### 4.5 平台保存的信息

平台至少保存以下信息，用于登记、展示和审计：  

- License 登记信息：appCode、licenceId、revision、LicenceData、有效期、模块；  
- 机器绑定与激活状态：machineCode、激活状态、首次激活时间、撤销记录、续期记录；  
- 运行状态：最近状态查询时间、撤销/续期通知发送时间、子应用确认时间、内存缓存更新结果、本地文件更新结果、剩余天数、模块暂停状态；  
- 审计日志：导入、验签、绑定、激活、撤销、续期、模块暂停、通知确认等操作及操作人。  

具体表结构由平台实现决定，本文不展开。  

### 4.6 状态聚合

#### 实例状态

| 状态               | 判定                                        |
| ---------------- | ----------------------------------------- |
| `NOT_ACTIVATED`  | 已登记但未完成首次激活                               |
| `ACTIVE`         | 已激活、未撤销、未过期，且剩余天数大于预警阈值                   |
| `EXPIRING`       | 已激活且进入预警期                                 |
| `CRITICAL`       | 已激活且进入严重预警期                               |
| `EXPIRED`        | 已过期                                       |
| `REVOKED`        | 平台已撤销，且子应用已确认内存缓存和本地文件更新成功，或启动查询时已按撤销状态更新 |
| `REVOKE_PENDING` | 平台已发起撤销，尚未收到子应用确认                         |
| `REVOKE_FAILED`  | 通知、内存缓存或本地文件更新、确认失败，平台页面需展示失败并重试          |
| `INVALID`        | 验签、机器码、appCode 等异常                        |

本方案没有心跳，因此不定义基于心跳的 `OFFLINE` 状态。  

续期通知失败不改变实例的授权状态（旧 Licence 继续按原有效期判定），不作为实例状态，但属于通知异常，需要在页面展示并告警。  

#### 应用状态

- 以 `appCode` 聚合；  
- 应用剩余天数取所有机器码中的最小值；  
- 应用状态取最严重实例状态；  
- 撤销待确认、撤销失败、续期通知失败、无效状态均视为异常；  
- 模块状态：  
  - 所有机器码都启用 → `ENABLED`  
  - 部分机器码启用 → `PARTIAL`  
  - 都未启用 → `DISABLED`  
  - 已过期 → `EXPIRED`  

#### 已授权应用口径

- **子应用总数**：平台已登记或已上报的 appCode 数量；  
- **已授权应用**：至少有一个机器码处于 `ACTIVE` 或 `EXPIRING` 的 appCode 数量；  
- 未激活、已撤销、已过期不计入“已授权应用”。

#### 启动参数建议

部署人员只有 jar 包时，可用以下启动参数：  

```bash
java -jar app.jar \  --licence-cache=./licence.txt \  --licence-public-key=<可选固定公钥或文件路径>  
```

| 配置              | 输入方式                   | 说明                                                    |
| --------------- | ---------------------- | ----------------------------------------------------- |
| 本地 Licence 文件路径 | `--licence-cache`      | 可选；默认 `./licence.txt`；子应用读写该文件并同步内存缓存                 |
| 固定 RSA 公钥       | `--licence-public-key` | 可选；支持 Base64 / PEM / 文件路径；不配置时使用平台下发公钥；配置后必须与平台下发公钥一致 |
| 禁用授权            | `--licence-enable`     | 可选；设为 `false` 仅用于开发调试                                 |
| 集成平台地址与鉴权       | 复用子应用已有的平台接入配置         | 不需要在 Licence 参数中重复配置                                  |
| `appCode`       | 复用已有的平台接入配置            | 首次激活前尚未获得 Licence，不能从 Licence 解析                      |
| `machineCode`   | 子应用运行时自动读取             | 不需要通过启动参数传入                                           |
| 授权码             | 不单独传参                  | 首次激活时从平台获取，写入本地文件并载入内存缓存                              |

说明：  

- 子应用本身已接入集成平台，登录、权限和接口鉴权已有现成配置；Licence 的激活和查询直接复用这套平台客户端和凭据，不再单独配置平台地址或 token。  
- 激活和状态查询发生在启动阶段，应复用子应用的应用级平台接入凭据，不能依赖某个用户登录后的 token。  
- 子应用默认从平台获取验签公钥，并支持通过 `--licence-public-key` 固定公钥；平台返回的公钥和授权码必须验签后才能使用；如配置了固定公钥，平台返回的公钥与其不一致时拒绝。  
- 本地文件和内存缓存只保存公钥和签名数据，不保存任何私钥。  

### 5.2 启动流程

```text
子应用启动  
  ↓检查本地 licence.txt 是否存在（仅用于判断是否首次启动，不直接作为授权结果）  
  ├─ 不存在（首次启动）  
  │   → 必须联网  
  │   → 调授权信息获取接口，取得授权码和公钥  
  │   → 本地验签 → 调激活接口  
  │   → 生成 licence.txt  │   → 载入内存缓存 → 启动成功  
  │   （平台不可达或激活失败 → 启动失败）  
  └─ 存在  
      → 优先联网查询平台状态  
      ├─ 在线：  
      │   ├─ 平台状态有效且无更高 revision → 以平台状态更新本地文件和内存缓存  
      │   ├─ 平台返回更高 revision（续期）→ 验签后替换本地文件和内存缓存  
      │   └─ 已撤销 / 已过期 / 无效 / 业务拒绝 → 更新本地文件和内存缓存 → 启动失败  
      └─ 网络不可用（连接失败 / 超时 / 5xx）：  
          → 读取本地 licence.txt 并验签  
          ├─ 本地文件有效、未被撤销、未过期 → 载入内存缓存 → 离线启动  
          └─ 否则 → 启动失败  
  ↓建立 SSE 通知连接，启动接口拦截  
  ↓运行期接口拦截只读内存缓存  
```

要点：  

- 首次激活必须联网；  
- 启动时优先以平台状态为准；仅当网络错误、超时或平台不可用时才信任本地文件；  
- 平台明确返回未登记、未激活、已撤销、已过期等业务错误时，必须启动失败，不能降级到本地文件；  
- 本地文件验签失败按无本地文件处理，不得降级放行；  
- 启动成功后，最终选定的 Licence 信息必须载入内存缓存；运行期接口拦截只读内存缓存；  
- 平台返回撤销或续期状态时，同时更新本地文件和内存缓存，再决定启动或阻断；  
- 平台返回的 revision 低于本地记录时按异常处理，保留本地版本并告警，不得回退。  

### 5.3 三份 Licence 数据与读写规则

子应用运行期涉及三份 Licence 数据：  

| 份数  | 数据源                | 作用                                                | 读取时机               | 更新方式              |
| --- | ------------------ | ------------------------------------------------- | ------------------ | ----------------- |
| 1   | 集成平台               | 启动时的权威来源；首次激活、状态查询、撤销/续期通知                        | 首次激活；每次联网启动；通知到达   | 平台返回结果            |
| 2   | 本地文件 `licence.txt` | 持久化副本；网络不可用时的启动兜底                                 | 启动时检查是否存在；平台不可用时读取 | 激活、启动查询、通知处理后原子写入 |
| 3   | 内存缓存               | 运行期 Licence 状态（授权码、revision、模块状态、撤销状态）；接口拦截的唯一读取源 | 每次接口或任务入口          | 启动成功后载入；通知到达时同步更新 |

读写规则：  

1. 启动时先判断本地文件是否存在：存在时优先联网查询平台，平台不可用再读取本地文件；不存在时必须联网首次激活；  
2. 启动成功后，把最终选定的 Licence 信息载入内存缓存；之后的接口拦截只读内存缓存，不访问平台或本地文件；  
3. 平台撤销/续期通知到达时，必须同时更新内存缓存和本地文件，两者均成功才算处理成功；任一失败返回失败结果，由平台展示并重试；  
4. 通知失败或子应用离线时，平台展示执行失败；子应用下次联网启动查询时完成补偿；  
5. 内存缓存是运行期唯一判定依据，本地文件是重启恢复依据；两者 revision 不一致时，以更高 revision 且验签通过者为准；涉及撤销时按更严格状态处理；  
6. 接口拦截不得在每次请求时读取平台或本地文件，避免性能问题和状态不一致；  
7. 内存缓存不可用或初始化失败时按 fail-closed 处理，拒绝接口访问；  
8. 内存缓存不持久化，重启后必须由平台结果或本地文件重新构建。  

### 5.4 运行期流程

本方案没有心跳。运行期授权状态由子应用在本地判定，状态变更来自平台通知：  

```text
平台撤销 / 续期 / 暂停模块  
  ↓SSE 通知通道（平台 → 子应用）  
  ↓子应用验签通知（RENEW 还需验签新的 LicenceData）  
  ├─ REVOKE → 内存缓存置为 REVOKED，原子改写本地 licence.txt，返回确认  
  ├─ RENEW → 验签新 Licence、校验 revision 递增 → 写本地文件 → 切换内存缓存 → 返回确认  
  ├─ SUSPEND_MODULE → 内存缓存暂停对应模块，改写本地文件，返回确认  
  └─ RESUME_MODULE → 内存缓存恢复对应模块，改写本地文件，返回确认  
  ↓通过 HTTPS 确认接口回传 memoryUpdated / fileUpdated  ↓运行期接口拦截读取内存缓存  
  ↓平台记录确认结果；内存缓存或本地文件更新失败则展示执行失败并重试  
```

补充约定：  

- 通知丢失或子应用离线时，平台展示“撤销待确认/撤销失败”或“续期通知失败”；  
- 子应用下次联网启动时会查询平台状态，完成补偿；  
- 离线实例在收到通知或下次启动查询前，仍可能按内存缓存运行，这是本方案的已知残余风险；  
- 不得通过轮询、定时任务或心跳替代通知机制；  
- 接口拦截只读内存缓存，不得在请求链路中读取平台或本地文件。  

### 5.5 模块拦截实现建议

子应用可以选择以下方式之一：  

- **注解 + 拦截器/AOP**：在模块入口标注模块编码，统一校验；  
- **请求路径映射**：在过滤器/网关中按路径前缀匹配模块；  
- **业务入口显式校验**：在模块的服务入口调用统一的模块校验函数。  

要求：  

- 拦截点覆盖所有入口：HTTP Controller、定时任务、MQ 消费者、批处理作业、WebSocket、内部 RPC、异步任务、文件导入导出、缓存刷新任务等；  
- 默认 fail-closed：未标注或未分类的入口视为未授权；始终启用的基础功能必须显式声明为基础模块；  
- 未授权模块返回 403 和明确错误码；  
- 模块暂停只影响对应模块，不阻断整个应用；  
- 拦截时只读内存缓存，不访问集成平台或本地 `licence.txt`；内存缓存不可用时 fail-closed；  
- 前端隐藏菜单只能作为体验优化，不能替代服务端拦截。  

### 5.6 本地 Licence 文件

本地 Licence 文件由子应用在激活成功后生成，建议采用 UTF-8 JSON 文本，文件名为 `licence.txt`。  

示例：  

```json
{  
  "cacheVersion": 1,  "licenceCode": "<Base64 授权码>",  
  "licencePublicKey": "<Licence 公钥>",  
  "platformPublicKey": "<平台通知验签公钥>",  
  "licenceKeyId": "licence-key-2026",  "platformKeyId": "platform-key-2026",  "licenceId": "LIC-20261022-0001",  "revision": 1,  "appCode": "performance",  "machineCode": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",  "status": "ACTIVE",  "moduleStates": {    "performance.report": "ENABLED"  },  "revocationNotice": null,  "lastSyncAt": "2026-10-23T10:00:00+08:00",  "checksum": "<本地文件校验和>"  
}  
```

要求：  

- `licenceCode` 是平台下发的已签名 LicenceData，加载时必须验签；  
- `revocationNotice` 是平台签名的撤销通知，必须验签，不能只依赖 `status` 字段；  
- 续期时，新的 `licenceCode`、`revision`、`licenceKeyId` 和有效期替换旧值，旧版本不得保留为可回退版本；  
- `status` 仅用于展示；离线授权判定以授权码和撤销通知的验签结果为准，`status` 与签名数据不一致时按更严格结果处理；  
- `checksum` 只用于检测文件损坏，不作为安全边界；  
- 写入采用“临时文件 + 落盘 + 原子重命名”，避免断电或并发导致文件损坏；  
- 激活成功后本地文件写入失败时，子应用应启动失败并提示本地文件路径或权限问题，不得静默忽略；  
- 文件权限限制为运行用户可读写；Windows 环境按同等原则设置 ACL；  
- 本地文件损坏、验签失败或机器码不一致时，视为无本地文件；此时必须联网重新激活；  
- 本地文件是持久化副本，必须与内存缓存同步更新；运行期接口拦截不读取该文件；  
- 本地文件不保存任何私钥，也不在日志中输出完整授权码。  

### 5.7 状态通知处理（SSE 客户端）

子应用启动成功后建立并保持 SSE 通知连接，实现：  

1. 建连时同时携带 `appCode`、`machineCode` 和平台凭据；`appCode + machineCode` 必须与本次激活/查询使用的实例身份一致；  
2. SSE 读取线程只负责收帧和入队，通知由单线程按到达顺序处理并确认，避免并发更新内存缓存和本地文件导致状态乱序；  
3. 按 `noticeId` 幂等处理，重复通知不得重复变更状态；已处理通知再次到达时直接回传上次确认结果；  
4. 校验通知签名、`platformKeyId`、时间窗、`nonce`、`machineCode`、`licenceId` 和 `action`；  
5. `RENEW` 时额外使用 `licenceKeyId` 对应的公钥验签新的 LicenceData，校验 `appCode`、`machineCode` 和 `revision` 递增；验签失败或版本回退时拒绝更新；  
6. 同时更新内存缓存和本地文件，更新顺序同 4.4：  
   - `REVOKE`：先把内存缓存置为 `REVOKED` 立即阻断，再原子改写 `licence.txt`；  
   - `RENEW`：先把新 Licence 原子写入 `licence.txt`，成功后再切换内存缓存；  
   - `SUSPEND_MODULE` / `RESUME_MODULE`：先更新内存中的模块状态立即生效，再原子改写 `licence.txt`；  
7. 通过 HTTPS 确认接口回传 `memoryUpdated` 和 `fileUpdated`；两者均为成功才算处理成功；确认失败按同一 `noticeId` 退避重试，但不得重复改状态；  
8. 收到 `stream-ready` 时，比较事件携带的平台 `currentRevision`、`status`、`lastNoticeId` 与本地内存缓存，任一不一致则立即调用启动状态查询接口对齐；  
9. 收到 `replay-required` 时立即调用启动状态查询接口，成功后用最新状态重新建连；  
10. 连接断开时按 6.3 的退避策略重连；断线期间继续按内存缓存运行（已撤销状态仍按内存缓存阻断），不得因 SSE 断线阻断正常业务；  
11. 建连、重连、补发、确认失败均记录日志和指标；不得用轮询替代 SSE，也不得引入 MQ 客户端。

## 六、平台接口与通信协议

### 6.1 统一身份约定（appCode + machineCode）

子应用对集成平台的每一次 Licence 相关请求都必须同时携带 `appCode` 和 `machineCode`：  

| 参数            | 位置                                       | 必填  | 说明                  |
| ------------- | ---------------------------------------- | --- | ------------------- |
| `appCode`     | HTTPS 请求头 `X-App-Code`；SSE 建连时放入查询参数     | 是   | 子应用唯一标识，复用已有平台接入配置  |
| `machineCode` | HTTPS 请求头 `X-Machine-Code`；SSE 建连时放入查询参数 | 是   | 本机机器码，子应用运行时读取；不是秘密 |
| 平台凭据          | 请求头 `Authorization` 等                    | 是   | 复用子应用已有的平台接入凭据      |

要求：  

- 平台以 `(appCode, machineCode)` 为唯一键定位 Licence；只带 `appCode` 或只带 `machineCode` 的请求一律拒绝；  
- `licenceId` 可用于一致性校验和审计，但不能替代 `(appCode, machineCode)` 作为定位键；  
- 平台必须校验 `appCode` 与请求凭据绑定的应用一致，防止越权读取其他应用的 Licence；  
- 缺少身份参数、身份与凭据不匹配或实例未登记时返回 400/403，且不返回任何 Licence 内容；  
- 平台只返回该实例的一份有效 Licence（最高 `revision`），不得返回同一应用下其他机器码的数据；  
- 首次启动拉取授权文件（LicenceData / 授权码）时，平台按 `(appCode, machineCode)` 返回该实例唯一一份有效 Licence；平台返回前必须完成验签和登记校验，子应用收到后必须再次本地验签；  
- `machineCode` 规范化规则见 2.1。  

### 6.2 HTTPS 接口

| 接口     | 方法与路径（建议）                                               | 请求身份                           | 作用                                                                       | 调用时机        |
| ------ | ------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------ | ----------- |
| 授权信息获取 | `POST /api/platform/app-licence/activation-info`        | 凭据 + `appCode` + `machineCode` | 平台校验登记和机器码绑定，返回本机授权码、Licence 公钥、平台通知验签公钥、keyId、licenceId、revision、有效期和模块 | 首次启动        |
| 激活     | `POST /api/platform/app-licence/activate`               | 凭据 + `appCode` + `machineCode` | 子应用本地验签后调用，平台标记激活并返回激活结果                                                 | 首次启动        |
| 授权状态查询 | `POST /api/platform/app-licence/status`                 | 凭据 + `appCode` + `machineCode` | 返回本机当前授权状态、撤销/续期/暂停状态、剩余天数，如有更高 revision 的 LicenceData 一并返回              | 每次启动且网络可用   |
| 通知确认   | `POST /api/platform/app-licence/notices/{noticeId}/ack` | 凭据 + `appCode` + `machineCode` | 回传通知处理结果和内存/文件更新结果                                                       | 处理完 SSE 通知后 |

说明：  

- 路径为建议命名，平台可按现有 API 规范调整；调整时 `appCode + machineCode` 的必填语义和接口作用不得改变；  
- 所有 HTTPS 接口的响应包含 `requestId`、`timestamp`、`code`、`message`、`data`，并使用平台独立密钥签名；子应用按 `platformKeyId` 验签并校验时间窗和 `nonce`；  
- 子应用解析平台下发的授权码时必须本地验签；收到更新版 LicenceData 时也必须再次验签，不能只信任平台的“已激活”返回；  
- 首次激活失败时子应用启动失败，并记录明确原因；  
- 启动状态查询仅在网络错误、超时或平台不可用时使用本地文件；平台返回未登记、未激活、已撤销、已过期等业务错误时，子应用必须启动失败；  
- 通知确认必须幂等，重复确认返回相同结果，不得回滚已完成的更新；  
- 本方案不提供心跳接口。  

### 6.3 SSE 通知通道

#### 6.3.1 建立连接

子应用启动成功、完成首次激活或启动状态查询后，建立 SSE 长连接：  

```http
GET /api/platform/app-licence/notices/stream?appCode=performance&machineCode=9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08 HTTP/1.1  
Host: platform.example.com  
Authorization: Bearer <复用平台接入凭据>  
Accept: text/event-stream  
Cache-Control: no-cache  
Last-Event-ID: <上次最后处理的通知 ID，可选>  
```

平台响应：  

```http
HTTP/1.1 200 OK  
Content-Type: text/event-stream; charset=utf-8  
Cache-Control: no-cache  
Connection: keep-alive  
X-Accel-Buffering: no  
```

规则：  

- 每个 `(appCode, machineCode)` 只保留一条有效连接；同一实例重复建连时，平台关闭旧连接并以最新连接为准；  
- 平台校验连接携带的 `appCode + machineCode`、平台凭据和实例登记状态，任一不通过时拒绝建连（401/403），不建立事件流；  
- 连接建立后，平台先发送 `stream-ready` 事件，携带服务器时间以及该实例当前的 `currentRevision`、`status` 和 `lastNoticeId`，供子应用判断本地状态是否落后；  
- 平台默认每 15 秒发送一次 SSE 注释行 `: ping` 保活，不产生业务事件；  
- 子应用连续 60 秒未收到任何数据（事件或 ping）时判定连接失效，主动重连；  
- 重连采用指数退避 + 抖动，默认 1s、2s、4s、8s、16s、30s、60s 封顶。  

#### 6.3.2 事件格式

SSE 事件帧：  

```text
id: NTC-20261026-0001  
event: licence-notice  
data: {"noticeId":"NTC-20261026-0001","action":"RENEW","licenceId":"LIC-20261022-0001","appCode":"performance","machineCode":"9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08","revision":2,"licenceCode":"...","licencePublicKey":"...","licenceKeyId":"licence-key-2026","issuedAt":"2026-10-26T10:00:00+08:00","nonce":"...","reason":"续期","platformKeyId":"platform-key-2026","signature":"..."}  
```

| 字段      | 说明                                                            |
| ------- | ------------------------------------------------------------- |
| `id`    | 等于 `noticeId`；子应用重连时作为 `Last-Event-ID` 回传                     |
| `event` | 业务事件为 `licence-notice`；系统事件为 `stream-ready`、`replay-required` |
| `data`  | 单行 JSON，内容与 4.4 通知体一致；不得包含换行，建议不超过 256 KB                     |

事件类型：  

| `event`           | 含义                                     | 子应用处理                                                                 |
| ----------------- | -------------------------------------- | --------------------------------------------------------------------- |
| `licence-notice`  | 撤销/续期/模块暂停或恢复通知                        | 验签、更新内存和本地文件、HTTPS 确认                                                 |
| `stream-ready`    | 连接就绪                                   | 比较 `currentRevision`、`status`、`lastNoticeId` 与本地内存缓存，任一不一致时调用状态查询接口对齐 |
| `replay-required` | 平台无法按 `Last-Event-ID` 补发（超出保留期或 ID 无效） | 立即调用启动状态查询接口，成功后重新建连                                                  |

#### 6.3.3 断点续传与重放

- 平台为每个 `(appCode, machineCode)` 保存通知记录和确认状态，保留期默认 7 天；  
- 子应用重连时携带标准请求头 `Last-Event-ID`；平台也可支持 `lastEventId` 查询参数，二者固定其一，避免语义不一致；  
- 平台按发送顺序补发该实例未确认的通知，补发完成后再推送新通知；  
- `Last-Event-ID` 早于保留期或平台无法定位时，平台发送 `replay-required`，不直接补发；  
- SSE 是至少一次投递；子应用必须按 `noticeId` 幂等处理，重复通知不得造成状态回退；  
- 平台记录每个 `(appCode, machineCode)` 的连接状态（`CONNECTED` / `DISCONNECTED` / `REPLAY_REQUIRED`）、最近连接时间和最近确认时间，供页面展示。  

#### 6.3.4 断线与补偿

- SSE 断开或建连失败不等于 Licence 失效：子应用按内存缓存继续运行，不得因通知通道断开阻断正常业务；已撤销状态仍按内存缓存阻断；  
- 平台在页面展示“通知未送达/待确认/通道未连接”，并在子应用重连时补发；  
- 子应用下次联网启动时调用授权状态查询接口，平台返回最新撤销/续期/模块暂停状态，完成补偿；  
- 通知超过保留期仍未确认时，以启动状态查询结果为准，平台在页面保留失败记录。  

### 6.4 通知确认

SSE 只能由平台向子应用推送，子应用处理后必须通过独立 HTTPS 接口确认：  

```http
POST /api/platform/app-licence/notices/NTC-20261026-0001/ack HTTP/1.1  
Host: platform.example.com  
Authorization: Bearer <复用平台接入凭据>  
X-App-Code: performance  
X-Machine-Code: 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08  
Content-Type: application/json  

{  
  "noticeId": "NTC-20261026-0001",  "action": "REVOKE",  "revision": 1,  "memoryUpdated": true,  "fileUpdated": true,  "appliedAt": "2026-10-26T10:00:00+08:00",  "reason": null}  
```

要求：  

- 只有 `memoryUpdated=true` 且 `fileUpdated=true` 才算成功；任一为 `false` 时 `reason` 必须说明原因；  
- 平台收到成功确认后才把通知标记为完成；失败或超时（默认 30 秒）标记为待重试，在同一 SSE 连接上重发同一 `noticeId`，连接恢复后补发；  
- 确认接口幂等：同一 `noticeId` 重复确认返回相同结果，不得回滚已完成的更新；  
- 子应用确认请求失败时按指数退避重试，但不得重复修改状态；  
- 平台不得仅凭 SSE 连接存活推断通知已成功。  

### 6.5 交互时序

```text
首次启动：  
子应用 → HTTPS 授权信息获取（appCode + machineCode）  
子应用 ← 授权码、公钥、keyId、licenceId、revision、有效期、模块  
子应用 本地验签  
子应用 → HTTPS 激活（appCode + machineCode）  
子应用 ← 激活成功  
子应用 生成 licence.txt，载入内存缓存  
子应用 → HTTPS 授权状态查询（appCode + machineCode，可选）  
子应用 ← 当前状态和最新 revision子应用 → SSE 建连（appCode + machineCode，Last-Event-ID 可选）  
平台 → SSE stream-ready平台 保存连接状态  

运行期：  
平台 → SSE licence-notice子应用 验签、按 noticeId 幂等处理  
子应用 更新内存缓存和 licence.txt子应用 → HTTPS 通知确认（noticeId + memoryUpdated + fileUpdated）  
平台 ← 确认成功，标记完成  
平台 页面刷新通知状态  
```

### 6.6 不采用的通道

- **不引入消息队列（MQ）**：避免新增中间件、网络开通和运维成本；SSE 已满足单向通知需求；  
- **不使用 WebSocket**：本场景不需要子应用向平台持续发送消息，SSE 足够；确认使用普通 HTTPS；  
- **不要求子应用轮询通知**：断线补偿由 SSE 重连和启动状态查询完成；  
- 平台多实例部署时，通知如何投递到持有 SSE 连接的实例属于平台内部实现，可通过网关粘性路由、共享连接注册表或内部转发实现，客户端协议不感知，也不需要 MQ。

## 七、安全与密钥管理

1. **私钥离线**：RSA 私钥只在生成脚本/离线签名环境/HSM 中保存，不得进入平台应用服务器、代码仓库、文档目录、部署包或镜像。  
2. **公钥可公开**：Licence 公钥和平台通知验签公钥可以分发；子应用默认从平台获取，也可通过 `--licence-public-key` 固定。  
3. **平台必须验签**：平台导入 LicenceData 时必须验证 checksum 和 RSA 签名，验签失败不得登记或激活。  
4. **子应用必须本地验签**：即使平台返回“已激活”，子应用仍要校验签名、appCode、machineCode、有效期，防止平台被攻破后伪造授权。  
5. **平台只能收紧或换发新 Licence**：平台可以撤销 Licence 或暂停已授权模块，但不能增加签名 LicenceData 之外的模块，也不能自行延长有效期；续期必须签发 `revision` 更高的新 LicenceData。  
6. **一机一 Licence**：平台激活记录必须绑定 machineCode，同一 `(appCode, machineCode)` 只能有一份有效 Licence；子应用本地也要校验 machineCode。  
7. **传输安全**：HTTPS + 复用子应用既有的平台鉴权机制，防篡改和重放；Licence 功能不单独管理平台凭据。  
8. **平台响应可信**：授权信息、激活结果、状态查询响应和撤销/续期通知使用平台签名或 mTLS；平台签名密钥与 Licence 签名密钥分离，子应用使用保存在本地文件和内存缓存中（或通过启动参数固定）的公钥验签。  
9. **本地文件与内存缓存安全**：`licence.txt` 必须原子写入、权限受控；加载时验签授权码和通知；内存缓存只能由验签通过的数据更新；接口拦截读取内存缓存，被篡改或损坏时按无授权处理。  
10. **通知防重放**：撤销/续期通知包含 `noticeId`、`timestamp`、`nonce`，子应用校验时间窗和 nonce，并按 `noticeId` 幂等处理。  
11. **审计**：记录 LicenceData 导入、验签、机器码绑定、激活、撤销、续期、模块暂停、通知确认等操作。  
12. **私钥泄露处理**：如果私钥曾进入 Git、共享目录、聊天工具或交付包，应立即轮换密钥对、重新签发所有 Licence，并更新平台和子应用公钥。  
13. **SSE 通道安全**：SSE 只允许 HTTPS；使用平台接入凭据鉴权，`appCode` 必须与凭据绑定的应用一致；长期凭据不得只放在 URL 中，`machineCode` 可以放在查询参数；凭据轮换或过期时子应用应断开并按新凭据重连；平台对同一 `(appCode, machineCode)` 只保留一条连接，并拒绝未登记实例建连。  
14. **通知确认安全**：确认接口同样校验 `appCode + machineCode` 和平台凭据；确认报文只表示子应用已处理通知，不得携带或接受任何可改变授权范围的字段；确认接口必须幂等。  
15. **请求身份校验**：所有 Licence 请求必须携带 `appCode + machineCode`，平台必须校验二者与凭据、登记记录一致；缺少身份参数或身份不匹配时，不返回任何 Licence 数据。

## 八、多部署环境机器码采集与硬件绑定方案

> 本章统一物理机、虚拟机、云主机、Docker / Kubernetes 容器化环境下 `machineCode` 的采集与生成标准，是 2.1 和 5.1 中“机器码获取”工作的落地规范。核心目标是确保机器码锚定底层**不可篡改的硬件或固件标识**，实现“一机一 Licence”的强绑定，杜绝授权文件跨机器随意迁移或通过环境变量伪造机器码。  
> 
> 本章生成的 `machineCode` 固定为 64 位小写十六进制 SHA-256 摘要，满足 2.1 的长度和字符集约束，并按 2.1 的规则原样比较。  

### 8.1 设计背景与安全原则

#### 8.1.1 多环境统一采集原则

为保证子应用在不同基础设施下具备一致的授权校验逻辑，机器码采集遵循**“算法完全统一、容器穿透底层”**的原则：  

- **物理机、虚拟机（VMware/KVM 等）、云主机（ECS/CVM 等）**：直接由子应用在操作系统层读取底层固件与硬件特征，采用完全一致的机器码生成逻辑。  
- **容器化环境（Docker / Kubernetes）**：由于容器默认隔离了宿主机硬件视图（容器内读取到的主板序列号常为 `unknown` 或 `default string`，虚拟网卡 MAC 地址随容器重建而漂移），必须通过**只读挂载宿主机硬件信息目录**的方式穿透隔离层，再执行与物理机完全相同的采集算法。  

#### 8.1.2 核心安全约束

1. **机器码的本质是“硬件绑定”而非“保密”**：  
   - 授权数据（LicenceData）由离线 RSA 私钥签名生成，子应用使用平台下发（或通过 `--licence-public-key` 固定）的公钥进行本地验签。机器码本身属于公开标识（可在日志或报错提示中直接打印），攻击者即便获知机器码，在无私钥的情况下也无法伪造签名授权码。  
2. **严禁通过环境变量或启动参数注入机器码**：  
   - 机器码必须由子应用在运行时**实时读取底层不可变硬件特征计算得出**，严禁接受环境变量或配置文件传入的机器码字符串。  
   - 若允许外部注入字符串，客户在机器 A 完成激活后，将容器与环境变量复制到机器 B 即可直接通过本地验签，导致“一机一码”硬件绑定彻底失效。  

### 8.2 统一硬件特征选型与采集优先级

为防止同一台服务器因后续挂载目录变更或安装系统工具导致机器码发生跳变，采集逻辑分为**“标准模式（默认）”**与**“硬件安全芯片模式（可选）”**，按固定优先级依次读取。  

#### 8.2.1 标准采集优先级（默认启用，覆盖 99% 场景）

| 优先级        | 采集特征项                              | 系统读取路径 / 方式                      | 不可篡改性说明                                         | 适用场景与优势                                        |
|:---------- |:---------------------------------- |:-------------------------------- |:----------------------------------------------- |:---------------------------------------------- |
| **P1（首选）** | **SMBIOS 整机 UUID（`product_uuid`）** | `/sys/class/dmi/id/product_uuid` | ★★★★（主板 BIOS 出厂写死或云厂商 Hypervisor 固化，操作系统层无接口可改） | **最通用主路径**：物理机、虚拟机、主流云主机及容器挂载均直接支持，无需安装额外命令行工具 |
| **P2（次选）** | **SMBIOS 主板序列号（`board_serial`）**   | `/sys/class/dmi/id/board_serial` | ★★★★（OEM 厂商出厂写入 EEPROM，需刷写硬件芯片才可更改）             | 当 `product_uuid` 为空或无效时的平滑降级                   |
| **P3（兜底）** | **主系统盘固件序列号 + CPU ID**             | `/dev/disk/by-id` + 处理器标识        | ★★★（磁盘固件烧录不可改，仅取固定主盘防止外接盘干扰）                    | 未暴露 DMI 信息的特殊精简虚拟化环境或老旧设备                      |

#### 8.2.2 硬件安全芯片模式（高安全物理机可选）

| 模式         | 采集特征项                     | 系统读取路径 / 方式                                | 不可篡改性说明                         | 启用条件                                                |
|:---------- |:------------------------- |:------------------------------------------ |:------------------------------- |:--------------------------------------------------- |
| **TPM 模式** | **TPM 2.0 背书密钥（EK 公钥指纹）** | `/dev/tpmrm0`（或 `/dev/tpm0`）+ `tpm2-tools` | ★★★★★（芯片出厂烧录，物理不可克隆 PUF 级，最强防伪） | 物理机具备 TPM 2.0 芯片且显式开启 TPM 采集策略时使用（避免与标准模式混用导致机器码跳变） |

> **有效性与异常阻断规则**：  
> 
> * 读取到的特征值若为空，或忽略大小写后匹配 `unknown`、`default string`、`none`、`to be filled by o.e.m.`、全 `0` / 全 `F` 等无效占位符，视为当前层级采集失败，自动降级至下一优先级。  
> * 若所有层级均无法获取有效特征，子应用必须**直接抛出异常并阻断启动**，严禁使用随机生成 UUID 或虚拟网卡 MAC 地址兜底。  

### 8.3 统一机器码计算规则

采集到原始硬件特征字符串后，统一去除首尾空白符、转为标准大写格式，添加**特征源前缀**后计算 **SHA-256** 十六进制摘要（小写）作为最终 `machineCode`：  

1. **命中 P1（整机 UUID）**：  
   - `machineCode = SHA256("UUID:" + normalize(product_uuid))`  
2. **命中 P2（主板序列号）**：  
   - `machineCode = SHA256("BOARD:" + normalize(board_serial))`  
3. **命中 P3（主盘序列号 + CPU 兜底）**：  
   - 遍历 `/dev/disk/by-id`，**剔除** `usb-*`（移动存储）、`dm-*`（LVM 逻辑卷）、`loop-*`、`md-*`（软阵列）及分区链接（`*-part*`），仅提取系统根分区所在物理磁盘（或按字典序排列的第一块固定硬盘 `ata-*` / `nvme-*` / `scsi-*`）的型号与序列号，确保后续扩容挂载数据盘或插拔 U 盘时机器码保持不变：  
   - `machineCode = SHA256("DISK:" + primaryDiskId + "|CPU:" + cpuId)`  
4. **若启用 TPM 模式**：  
   - 通过资源管理器 `/dev/tpmrm0` 读取 EK 公钥并计算指纹：  
   - `machineCode = SHA256("TPM:" + tpmEkPublicKey)`  

> 特征源前缀 `UUID:` / `BOARD:` / `DISK:` / `TPM:` 用于区分来源，避免不同硬件特征的原始值发生碰撞。  

### 8.4 各部署环境实施与运维规范

#### 8.4.1 物理机、虚拟机与云主机部署

1. **文件读取权限初始化（关键）**：  
   - Linux 系统中 `/sys/class/dmi/id/product_uuid` 与 `board_serial` 默认权限通常为 `0400`（仅 `root` 可读）。  
   - 当子应用遵循安全规范以**非 root 普通用户**（如 `appuser`）运行时，实施人员需在服务器初始化阶段执行一次赋权命令（或写入开机初始化脚本），赋予只读权限：  
     ```bash  
     sudo chmod 0444 /sys/class/dmi/id/product_uuid /sys/class/dmi/id/board_serial     ```2. **虚拟机克隆（VM Clone）注意事项**：  
   - 在 VMware vSphere、KVM 等虚拟化平台通过模板克隆多台虚拟机部署同一子应用时，必须在虚拟化管理平台勾选**“生成新的 BIOS UUID / 实例 UUID”**，防止克隆出的多台虚拟机拥有相同的 `product_uuid` 导致机器码冲突。  

#### 8.4.2 容器化部署（Docker / Kubernetes）

在容器化环境中，必须将宿主机的真实硬件标识目录**以只读（`ro`）方式挂载**至容器内。容器进程直接读取挂载路径下的宿主机文件，即便容器内拥有 `root` 权限也无法修改只读挂载源，从而实现与宿主机物理硬件的强绑定。  

> 若容器以非 root 用户运行，宿主机仍需按 8.4.1 对 DMI 文件执行 `chmod 0444`，否则容器内读取会被拒绝。  

**（1）Docker Compose 标准挂载配置**  

无需在业务镜像中安装额外硬件工具包，仅需挂载 DMI 目录、磁盘目录及本地 Licence 持久化文件：  

```yaml
version: '3.8'  
services:  
  sub-app:    image: sub-app:1.0.0    volumes:      # 1. 必选：只读挂载宿主机 SMBIOS/DMI 硬件标识目录（对应 P1、P2）  
      - /sys/class/dmi/id:/sys/class/dmi/id:ro      # 2. 必选：只读挂载宿主机磁盘 ID 目录（对应 P3 兜底）  
      - /dev/disk/by-id:/dev/disk/by-id:ro      # 3. 必选：持久化保存激活后的本地 licence.txt，防止容器重建丢失状态  
      - ./data/licence.txt:/app/licence.txt  
```

> 使用单文件 bind mount 时，必须在启动前先在宿主机创建 `./data/licence.txt`；否则 Docker 会在该路径创建同名目录，导致子应用读写失败。也可改为挂载目录 `./data:/app/data`，并通过 `--licence-cache=/app/data/licence.txt` 指定本地文件路径。  

**（2）Kubernetes (K8s) 部署挂载与固定节点调度**  

在 K8s 集群中，由于机器码锚定的是**宿主机工作节点（Worker Node）**，若 Pod 重建时被调度到其他节点，读取到的宿主机机器码将发生改变。因此必须遵循以下两项配置：  

1. **配置节点亲和性（`nodeSelector` / `nodeAffinity`）**：将受 Licence 管控的子应用 Pod 固定调度至已绑定机器码的宿主机节点。  
2. **只读挂载宿主机标识目录**：通过 `hostPath` 只读挂载 `/sys/class/dmi/id` 与 `/dev/disk/by-id`（普通目录只读挂载，无需申请容器 `privileged` 特权，符合企业 K8s 安全基线）。  

```yaml
apiVersion: apps/v1  
kind: Deployment  
metadata:  
  name: sub-appspec:  
  replicas: 1  template:    spec:      # 强制固定在已申请授权的宿主机节点运行，防止 Pod 漂移导致机器码改变  
      nodeSelector:        licence-authorized-node: "worker-node-01"      containers:        - name: sub-app          image: sub-app:1.0.0          volumeMounts:            - name: host-dmi              mountPath: /sys/class/dmi/id              readOnly: true            - name: host-disk              mountPath: /dev/disk/by-id              readOnly: true            - name: licence-storage              mountPath: /app/licence.txt      volumes:        - name: host-dmi          hostPath:            path: /sys/class/dmi/id            type: Directory        - name: host-disk          hostPath:            path: /dev/disk/by-id            type: Directory        - name: licence-storage          hostPath:            path: /data/sub-app/licence.txt            type: FileOrCreate  
```

### 8.5 机器码获取与生成端对齐流程

为保证集成平台授权生成脚本（KeyGen）登记的机器码与子应用运行期计算的机器码 100% 一致，提供以下两种标准获取途径：  

1. **宿主机独立采集工具（部署前预获取）**：  
   - 提供与子应用采集逻辑完全一致的轻量级命令行工具。  
   - 运维人员在目标物理机、云主机或 K8s 目标宿主机上直接运行该工具，即可输出本机标准 `machineCode`，交由平台管理员生成 `licence.json` 并导入集成平台。  
2. **子应用启动日志打印（部署时自检输出）**：  
   - 若子应用首次启动时平台尚未登记本机 Licence，子应用完成硬件采集后，将在启动失败日志及控制台明确打印本机识别码（如：`授权校验失败，本机机器码 [machineCode]: xxxxxxxx`）。  
   - 运维人员直接复制该机器码提交给管理员完成平台登记后，重启子应用即可自动完成首次激活。

## 十、验收标准

1. 生成脚本可以按 appCode、machineCode、有效期、revision、模块生成 `licence.json`；  
2. LicenceData 是脚本输出文本，平台登记；KeyGen 不再生成子应用本地 Licence 文件；  
3. 平台可以粘贴/上传 LicenceData，并完成验签、登记、绑定机器码和激活；  
4. 子应用首次启动可以从平台获取授权码和公钥，本地验签后完成激活，生成 `licence.txt` 并载入内存缓存；  
5. 再次启动且网络可用时，子应用优先通过平台查询本机 Licence 状态；  
6. 平台不可达时，子应用读取本地有效文件并启动；无本地文件或文件无效时启动失败；  
7. 启动成功后，接口拦截只读内存缓存，不访问平台或本地文件；内存缓存不可用时 fail-closed；  
8. 平台撤销 Licence 后，子应用收到通知，同时更新内存缓存和本地文件并返回确认；平台可展示确认结果；  
9. 平台续期时，子应用验签新的 LicenceData、校验 revision 递增，同时更新内存缓存和本地文件并返回确认；  
10. 撤销/续期通知未送达、子应用未确认或内存/文件任一更新失败时，平台展示执行失败，并在下次启动查询时补偿；  
11. 未授权或已过期模块的接口返回 403，其他模块不受影响；  
12. 平台暂停模块后，仅对应模块不可用；  
13. 子应用对定时任务、MQ、批处理、WebSocket 等非 HTTP 入口同样实施模块拦截；  
14. 平台可以按 appCode 展示应用状态、有效期、剩余天数、模块状态、机器码明细和通知状态；  
15. 平台完整记录导入、激活、撤销、续期、模块暂停和通知确认操作；  
16. 同一 `(appCode, machineCode)` 只能存在一份有效 Licence，旧 revision 不能覆盖新 revision；  
17. 本地文件被篡改或损坏时，子应用拒绝加载并按无本地文件处理；  
18. 子应用对平台的每个 Licence 请求都同时携带 `appCode` 和 `machineCode`；缺少任一项时平台拒绝且不返回 Licence；  
19. 平台以 `(appCode, machineCode)` 唯一键定位 Licence，同一应用的其他机器码数据对该实例不可见；  
20. 子应用通过 SSE 接收通知，通过独立 HTTPS 接口确认；不依赖 MQ 或 WebSocket；  
21. SSE 断线重连时携带 `Last-Event-ID`，平台补发未确认通知；重复通知按 `noticeId` 幂等，不造成状态回退；  
22. SSE 不可用或断线期间，子应用按内存缓存继续运行；下次启动查询时平台完成状态补偿；  
23. 物理机、虚拟机、云主机与容器化环境按第八章生成一致的机器码；容器挂载宿主机 DMI 与磁盘目录后可读到有效硬件特征；  
24. 硬件特征为空或为无效占位符时按 P1 → P2 → P3 降级，全部失败时阻断启动，不使用随机 UUID 或虚拟网卡 MAC 兜底；  
25. 机器码不接受环境变量或启动参数注入，子应用启动失败时日志可打印本机机器码用于平台登记。

## 十一、可选 SDK 方案

> 本章只说明可选方向，不作为本文的实施前提。  

当前方案默认由各子应用自行实现客户端能力。随着子应用数量增加，重复实现会带来：  

- 各子应用验签、激活、本地文件和内存缓存、通知处理逻辑不一致；  
- 模块拦截方式不统一，容易出现遗漏；  
- 协议升级需要逐个改造，维护成本高；  
- 错误处理和日志格式不统一，排查困难。  

我们可以额外提供一套 Licence SDK，作为独立工作项推进。**SDK 的设计、开发、测试、文档和发布需要额外工时/人天，需单独立项评估。**  

### 11.1 SDK 可以提供的功能

- 配置自动装配（appCode、本地文件路径、可选固定公钥；平台地址和鉴权复用子应用已有配置）；  
- LicenceData 解析、checksum 和 RSA 验签；  
- appCode、machineCode、有效期、revision 校验；  
- 首次激活与授权信息获取客户端；  
- 启动状态查询客户端；  
- 本地 `licence.txt` 文件读写、原子更新和内存缓存同步；  
- 启动成功后 Licence 信息载入内存缓存；  
- SSE 通知客户端：建连、重连、断点续传、通知验签、内存与文件同步更新和 HTTPS 确认；  
- 模块拦截注解/拦截器，读取内存缓存，覆盖 HTTP 和非 HTTP 入口；  
- 启用模块查询接口；  
- 统一错误码、日志和指标；  
- 失败重试、超时和错误处理模板；  
- 与 Spring Boot 等框架的自动配置集成。  

### 11.2 SDK 的优势

- 子应用接入从“自行实现一套客户端”简化为“引入依赖 + 少量配置”；  
- 所有子应用行为一致，减少验签、本地文件和内存缓存、模块拦截的遗漏；  
- 协议升级只需升级 SDK，降低逐个改造成本；  
- 统一日志、错误码和监控，便于平台侧排查；  
- 新子应用接入速度更快。  

### 11.3 SDK 的成本与前提

- 需要额外的设计、开发、测试、文档、发布和维护工时；  
- 需要适配子应用使用的框架和版本；  
- 需要制定 SDK 版本与 LicenceData 格式版本的兼容策略；  
- 需要独立的 SDK 使用文档和示例工程；  
- 如果子应用数量少、技术栈差异大，自行实现的综合成本可能更低。  

如确定采用 SDK，我们可以另行提供一份 SDK 方案文档，包含模块拆分、接入方式、版本策略和工时评估。

            │                           │                           │                           │ (原子写入 licence.txt + 载入内存)
            │                           │                           │◄── 7. 建立 SSE 长连接 ────│ GET /notices/stream
            │                           │                           │── 8. 推送 stream-ready ──►│ (激活闭环完成，正常运行)
            │                           │                           │                           │
```

1. **机器码采集**：运维人员在目标主机（含所有 HA 主备机、灾备机、K8s 授权池节点）运行独立采集工具，或直接启动子应用从启动失败日志中复制打印的 `machineCode`。
2. **离线生成 `licence.json`**：管理员执行 `java -jar keygen.jar --mode=cli --app-code=<应用编码> --machine-code=<机器码> --valid-from=<生效日> --expiry=<到期日> --modules-file=modules.json --revision=1 --output=licence.json` 生成签名授权文件。
3. **平台导入登记**：管理员将 `licence.json` 粘贴/上传至集成平台；平台校验 checksum 与 RSA 签名，绑定 `(appCode, machineCode)`。
4. **拉取授权与本地验签**：启动子应用，检测到本地无 `licence.txt`，调用 `POST /api/platform/app-licence/activation-info` 获取授权码与公钥，在本地完成签名、机器码与有效期校验。
5. **激活落盘与缓存加载**：子应用调用 `POST /api/platform/app-licence/activate` 激活成功后，以“临时文件 + 落盘 + 原子重命名”方式生成 `licence.txt`（若写入失败则阻断启动并提示权限/路径问题），将授权信息载入内存缓存，并建立 SSE 通知长连接。

### 12.2 流程二：续期流程（在线无感热续期 + 离线/免重启补偿）

```text
      [离线 KeyGen 环境]                    [院内集成平台]                      [子应用服务端]
              │                                   │                                   │
              │                                   │                                   │ (1. 管理员指定 --revision=2 签发)
              │─ 2. 导入新 licence.json (rev=2) ─►│                                   │
              │    (平台校验版本递增与签名)       │                                   │
              │                                   │                                   │
              │                                   │                                   │ 【分支 A：在线 SSE 实时热推送】
              │                                   │── 3. SSE licence-notice (RENEW) ─►│
              │                                   │     (携带新授权码/公钥/签名)      │
              │                                   │                                   │
              │                                   │                                   │ (4. 双重验签: 验平台通知 + 验新授权码)
              │                                   │                                   │ (5. 严格顺序: 先原子写文件，后切内存)
              │                                   │◄── 6. POST /notices/{id}/ack ─────│ (memory=true, file=true)
              │                                   │     (标记续期通知完成，展示成功)  │
              │                                   │                                   │
              │                                   │                                   │ 【分支 B：离线 / 无 SSE 环境状态补偿】
              │                                   │◄── 7. 重启或点击"手动同步"按钮 ───│ POST /status
              │                                   │── 8. 下发最新 rev=2 LicenceData ─►│
              │                                   │                                   │
              │                                   │                                   │ (热更新本地 licence.txt 与内存缓存)
              │                                   │                                   │
```

1. **查询当前版本**：管理员在平台查看目标 `(appCode, machineCode)` 当前的 `licenceId`（如 `LIC-001`）和 `revision`（如 `1`）。
2. **生成递增版本授权**：使用 `keygen.jar` 显式指定更大的 `--revision=2` 和 `--supersedes=LIC-001`，生成新 `licence.json` 并导入集成平台。
3. **平台验签覆盖与 SSE 推送**：平台校验 `revision` 递增与签名通过后替代旧版本，生成 `noticeId`，通过 SSE 向子应用推送 `action="RENEW"` 事件（携带新 `licenceCode`、`licencePublicKey`、`licenceKeyId`、`revision=2` 及平台签名）。
4. **子应用双重验签与安全切换**：
   - 子应用单线程处理队列校验平台通知签名、时间窗、`nonce` 及 `noticeId` 幂等性；
   - 使用 `licenceKeyId` 公钥验签新 LicenceData，确认 `appCode`、`machineCode` 匹配且 `revision > 本地版本`；
   - **严格执行“先持久化、后切内存”**：先将新 Licence 原子写入 `licence.txt`，写入成功后再切换内存缓存。
5. **回传确认**：子应用调用 `POST /api/platform/app-licence/notices/{noticeId}/ack` 回传 `memoryUpdated=true, fileUpdated=true`，平台标记续期通知完成。
6. **断线或无 SSE 环境补偿分支**：若推送时 SSE 断线或网关不支持 SSE，子应用在 SSE 重连（`Last-Event-ID` 补发或 `stream-ready` 触发查询）、管理员点击“手动同步授权状态”或下次联网重启调用 `POST /api/platform/app-licence/status` 时，自动拉取 `revision=2` 的新 LicenceData 完成更新。

### 12.3 流程三：撤销与模块暂停／恢复流程

```text
      [平台管理员 / 集成平台]                              [子应用服务端]
                │                                                   │
                │                                                   │ (1. 管理员发起 REVOKE 或 SUSPEND_MODULE)
                │                                                   │ (   平台状态置为 REVOKE_PENDING)
                │── 2. SSE 推送 licence-notice 事件 ─────────────►  │
                │     (携带 noticeId、action、时间戳、nonce、签名)  │
                │                                                   │
                │                                                   │ (3. 校验通知签名、nonce 与时间窗)
                │                                                   │ (4. 【先内存阻断】: 内存置为 REVOKED, 毫秒级阻断)
                │                                                   │ (5. 【后写文件】: 原子落盘改写本地 licence.txt)
                │                                                   │
                │◄── 6. HTTPS POST /notices/{noticeId}/ack ─────────│ (回传 memoryUpdated & fileUpdated)
                │                                                   │
                │                                                   │ (7. 平台判定确认结果，闭环处置)
                │                                                   │
          ┌─────────────────────────────┴─────────────────────────────┐
          ▼                                                           ▼
    [确认成功: memory & file 双成功]           [确认异常: 超时30s / 离线 / 失败]
                   │                                                           │
                   ├─ 状态更新为 REVOKED                                        ├─ 状态置为 REVOKE_FAILED
                   └─ 撤销流程顺利闭环                                          ├─ 触发平台高级别告警
                                                                                └─ 持续退避重发通知补偿
```

1. **平台发起指令**：管理员在平台对某实例执行“撤销 Licence”（`REVOKE`）或对某模块执行“暂停/恢复”（`SUSPEND_MODULE` / `RESUME_MODULE`）。
2. **SSE 推送与内存立即阻断**：
   - 平台将状态置为待确认并通过 SSE 推送签名事件；
   - 子应用验签通过后，**严格执行“先切内存阻断、后持久化”**：立即将内存缓存置为 `REVOKED`（或暂停对应模块），毫秒级阻断后续请求，随后将状态及平台签名的 `revocationNotice` 原子改写至本地 `licence.txt`。
3. **确认与失败重试闭环**：子应用通过 HTTPS `ack` 回传双更新结果；若 30 秒内未确认或任一更新为 `false`，平台展示 `REVOKE_FAILED`、触发高级告警并退避重发，直至重连确认或下次联网启动查询完成强制阻断。

### 12.4 流程四：换机与环境迁移标准流程

```text
    [旧机器环境 (Old)]                    [离线 KeyGen / 集成平台]                    [新机器环境 (New)]
              │                                     │                                     │
              │                                     │                                     │ 【阶段一：业务零中断运行中，旧机正常承接流量】
              │                                     │                                     │
              │                                     │◄── 1. 采集新宿主机硬件特征 ─────────│ (获取 machineCode_New)
              │                                     │── 2. keygen 签发并导入平台登记 ────►│ (绑定新机器码)
              │                                     │── 3. 新机子应用启动完成首次激活 ───►│ (生成本地 licence.txt)
              │                                     │                                     │
              │                                     │                                     │ 【阶段二：业务网络流量平滑切换至新机器】
              │◄── 4. 业务流量无缝切换至新节点 ─────│────────────────────────────────────►│
              │                                     │                                     │
              │                                     │                                     │ 【阶段三：旧机下线与旧授权撤销归档】
              │◄── 5. 平台执行 REVOKE 撤销旧机 ─────│                                     │ (释放旧机许可占用)
              │     (关闭旧机实例，审计归档)        │                                     │
              │                                     │                                     │
```

1. **新机预采集与预签发**：在目标新服务器或新 K8s Worker 节点采集新机器码 `machineCode_New`，通过 `keygen.jar` 签发新 `licence.json` 并导入集成平台登记（此时旧机继续运行）。
2. **新机启动与激活验证**：在新机启动子应用（K8s 调整节点亲和性标签），自动完成 `machineCode_New` 首次激活并切入业务流量。
3. **旧机撤销与下线归档**：确认新机运行正常后，管理员在集成平台对旧机 `(appCode, machineCode_Old)` 执行 `REVOKE` 撤销，关闭旧机实例，完成平滑迁移与审计留痕。

### 12.5 流程五：故障紧急恢复标准流程

```text
                                                  [子应用发生故障或重启]
                                                             │
                           ┌─────────────────────────────────┼─────────────────────────────────┐
                           ▼                                 ▼                                 ▼
                    【分支 A 场景】                    【分支 B 场景】                    【分支 C 场景】
                 网络中断 / 平台不可达              系统盘损坏 / 文件误删               主板损坏 / 整机宕机
                 (本地持久化文件存在)             (主板未换，机器码不变)             (底层机器码发生改变)
                           │                                 │                                 │
          ┌────────────────┴────────────────┬────────────────┴────────────────┬────────────────┴────────────────┐
          │ 1. POST /status 连接失败/超时   │ 1. 检测到无本地 licence.txt     │ 1. 评估现场备机资源情况:        │
          │                                 │                                 │    ├─► [情况 1：有预激活备机]   │
          │ 2. 自动触发离线降级启动:        │ 2. 自动调用平台激活接口:        │    │   直接切流量拉起服务,      │
          │    读取本地 licence.txt         │    POST /activation-info        │    │   业务即刻恢复!            │

          │                                 │                                 │    └─► [情况 2：全新未登记机器] │
          │ 3. 授权信息载入内存缓存放行!    │ 3. 平台按同一机器码幂等匹配:    │        从启动日志复制机器码,    │
          │    业务快速离线恢复，           │    直接下发原授权码并激活!      │        应急签发新 licence.json  │
          │    后台持续退避重连 SSE 通道    │ 4. 自动重建本地文件恢复业务!    │        导入激活，平台撤销旧机   │
          └────────────────┬────────────────┴────────────────┬────────────────┴────────────────┬────────────────┘
                           │                                 │                                 │
                           ▼                                 ▼                                 ▼
                  [离线降级自愈成功]                [同机幂等自愈成功]                [换机应急恢复成功]
```

- **分支 A：平台宕机或院内断网期间子应用紧急重启**
  1. 子应用启动检测到本地存在 `licence.txt`，请求平台 `POST /status` 遇到连接失败/超时/5xx。
  2. 自动读取本地 `licence.txt`，验证签名、硬件 `machineCode`、有效期及无撤销通知后载入内存缓存，立即离线启动恢复业务，并在后台启动 SSE 退避重连。

- **分支 B：系统盘损坏重装或容器本地文件丢失（主板未换，`machineCode` 不变）**
  1. 子应用启动检测到无 `licence.txt`（或文件损坏验签失败按无本地文件处理）。
  2. 自动携带原 `appCode + machineCode` 调用平台 `activation-info` 和 `activate` 接口；平台按幂等规则直接返回原授权码并激活，子应用重建 `licence.txt` 恢复运行，无需人工干预。

- **分支 C：主板损坏或整机宕机切换备用机（`machineCode` 改变）**
  1. 若切换至初验已预激活的 HA 备机/预置授权冷备机，直接拉起服务。
  2. 若切换至全新未登记服务器，从启动日志获取新 `machineCode`，提交我方应急签发通道获取新 `licence.json` 导入平台，重启子应用激活并在平台撤销损坏旧机 Licence。

### 12.6 流程六：应用升级与签名密钥轮换（Key Rotation）流程

```text
                     ┌─────────────────────────────────────────┐
                     │     应用版本升级与密钥轮换两类标准场景  │
                     └────────────────────┬────────────────────┘
                                          │
                    ┌────────────────────┴────────────────────┐
                    ▼                                         ▼
     ┌────────────────────────────┐            ┌────────────────────────────┐
     │ 【场景 1：子应用版本升级】 │            │ 【场景 2：密钥平滑轮换】   │
     ├────────────────────────────┤            ├────────────────────────────┤
     │ 1. 保持宿主机硬件与路径不变│            │ 1. 平台维护新旧公钥重叠表  │
     │    (--licence-cache 指定)  │            │    (旧 keyId 到期前仍有效) │
     │ 2. 替换 Jar 包或更新镜像   │            │ 2. 生成新授权指定新 keyId  │
     │ 3. 重启子应用服务端进程    │            │    (如 --key-id=key-2027)  │
     │ 4. 联网查询最新授权状态    │            │ 3. 首次激活或 RENEW 下发   │
     │    (断网自动降级读本地文件)│            │    新 keyId 对应验签公钥   │
     │ 5. 本地验签通过，业务恢复! │            │ 4. 子应用同步更新文件与内存│
     └─────────────┬──────────────┘            └─────────────┬──────────────┘
                   ▼                                         ▼
          [子应用升级平滑启动]                       [签名密钥轮换平滑切换]
```

- **子应用版本升级**：保持宿主机及 `--licence-cache`（`./licence.txt`）路径不变，替换 Jar 包或更新容器镜像后重启，子应用自动查询平台状态（或读本地文件）平滑启动。
- **RSA 密钥轮换升级**：
  1. 平台按 `keyId` 维护公钥版本表，新旧密钥保留重叠有效期，确保旧 `keyId` 未到期 Licence 继续有效。
  2. 新签发/续期的 `licence.json` 使用新密钥（如 `--key-id=licence-key-2027`）签名；平台在首次激活或 `RENEW` 通知中自动下发新 `keyId` 对应公钥，子应用同步更新至 `licence.txt` 与内存缓存（若配置了 `--licence-public-key` 固定公钥参数，则随维护窗口同步更新该参数）。

## 附录 D：问题与答复

### D.1 授权模型

**问**：LicenceData 绑定单一 `machineCode`，与“一份 Licence 支持多台机器激活”的表述不一致。  

**答**：实现就是一机一 Licence。LicenceData 必须绑定唯一 `machineCode`，平台按 `(appCode, machineCode)` 登记；同一机器码只能存在一份有效 Licence。多台机器部署时分别签发 Licence。续期通过更高 `revision` 替代旧 Licence；机器码变更需重新申请 Licence。  

### D.2 破解风险

**问**：仅由子应用自检授权，被改造的应用仍可能继续使用。  

**答**：破解软件是违法行为，且不存在不可破解的软件。本方案的目标是提高破解成本、保证合法客户的授权管理和审计，而不是承诺绝对不可破解。具体措施包括：LicenceData 签名校验、机器码绑定、本地文件和内存缓存验签、版本回退拒绝、平台撤销/续期通知和审计留痕。运行期授权由子应用控制，不额外依赖平台网关准入。  

### D.3 启动可用性

**问**：启动强依赖平台激活，平台或网络短暂故障会导致子应用批量无法重启。  

**答**：启动时优先联网去集成平台查询本机 Licence 状态；查询成功以平台结果为准，并同时刷新本地文件和内存缓存；仅网络不可用时读取本地 `licence.txt` 载入内存并继续启动；平台明确返回未登记、未激活、已撤销、已过期等业务错误时不得降级到本地文件；本地无文件或文件无效、已撤销、已过期时启动失败。首次激活必须联网，后续启动允许使用有效本地文件；启动成功后接口拦截只读内存缓存。  

### D.4 授权状态优先级与状态机

**问**：签名 LicenceData、平台撤销/续期/暂停状态、本地文件和内存缓存状态的优先级不清晰。  

**答**：统一决策顺序如下：  

1. 授权码签名、格式、`appCode`、`machineCode` 校验失败 → `INVALID`，直接拒绝；  
2. 本地存在经验签的撤销通知，或本次启动查询返回已撤销 → `REVOKED`，阻断业务；  
3. 平台暂停模块通知，或启动查询返回模块暂停 → 仅阻断对应模块；  
4. 当前时间早于 `validFrom` 或晚于 `expiryDate` → `EXPIRED`，阻断业务；  
5. 其余情况 → `VALID` / `EXPIRING` / `CRITICAL`；  
6. 多来源冲突时取更严格结果（fail-closed）；  
7. 平台只能收紧权限或签发更高 `revision` 的新 Licence，不能放宽签名 LicenceData；更新版 LicenceData 只有在 `revision` 更高且验签通过时才可替代本地版本；  
8. 平台不可达时，本地文件作为降级输入；文件无撤销通知且未过期时允许启动；  
9. 启动成功后，接口拦截以内存缓存为唯一读取源；内存缓存由平台结果或本地文件初始化，并由通知同步更新；  
10. 平台恢复可达后，以平台返回状态重新校准本地文件和内存缓存。  

状态迁移：  

```text
NOT_ACTIVATED → ACTIVE → EXPIRING → CRITICAL → EXPIRED  
                    │           │           │                    └───────────┴───────────┴──→ REVOKEDACTIVE/EXPIRING/CRITICAL → REVOKE_PENDING → REVOKED（收到确认）  
                                      └──→ REVOKE_FAILED（通知/内存或文件更新/确认失败，重试）  
REVOKED / EXPIRED / INVALID 不得自动恢复；只有平台签发更高 revision 的 Licence 后重新激活，才能回到 ACTIVE。  
```

### D.5 续期与版本回退

**问**：新旧 Licence 并存、平台下发更新、应用重启读取旧参数等场景未定义。  

**答**：已补充以下规则：  

- LicenceData 增加 `revision`（单调递增）和 `supersedesLicenceId`（替代关系）；  
- 同一 `(appCode, machineCode)` 下，新 Licence 的 `revision` 必须大于旧 Licence；  
- 子应用只接受 `revision` 大于本地已见版本的 Licence；相同 `revision` 但内容不一致时视为异常并告警；  
- 平台拒绝已替代 Licence 的再次激活；  
- 本地文件和内存缓存保存 last-known-good（含 `revision`、授权码和签名）；  
- 重启联网查询时，平台返回更高 `revision` 的 LicenceData，子应用验签后同时替换本地文件和内存缓存；  
- 平台续期通知携带新 LicenceData，子应用验签后同时更新内存缓存和本地文件；  
- 重启离线时使用本地文件中的最高 `revision`，不得回退到启动参数或旧文件中的低版本；  
- 验收增加“拒绝版本回退”用例。  

### D.6 机器码稳定性

**问**：云主机、虚拟机、容器、网卡或硬件变更可能导致合法实例失效。  

**答**：机器码变更需重新申请 Licence。平台不自动放行机器码变更；管理员应撤销旧 Licence，再按新机器码重新签发并登记。为减少变更，机器码采集固定硬件特征优先级，排除容器临时 ID 和虚拟网卡等不稳定标识，并通过特征源前缀（`UUID:` / `BOARD:` / `DISK:` / `TPM:`）区分特征来源后统一计算 SHA-256 摘要，写入 LicenceData 的 `machineCode` 字段并纳入签名。机器码的采集优先级、SHA-256 计算规则、容器只读挂载和 K8s 固定节点调度要求见第八章。机器码变更、撤销和重新签发均需留审计记录。  

### D.7 心跳策略

**问**：心跳周期、超时、重试、最长撤销生效时间和离线策略不明确。  

**答**：去除心跳策略。本方案不再设置心跳接口、心跳周期、超时和重试。运行期授权由子应用本地判定，接口拦截只读内存缓存；平台撤销、续期或暂停模块时通过通知通道告知子应用，子应用同时更新内存缓存和本地文件；启动时优先联网查询平台状态；通知失败或离线时由平台页面展示执行失败，并在下次启动查询时补偿。  

### D.8 签名协议标准化

**问**：JSON 规范化、RSA 参数、`keyId`、密钥轮换和平台响应签名/防重放机制未定义。  

**答**：已按以下规则补充：  

- 规范化使用 RFC 8785（JCS），UTF-8 编码，去除 `checksum` 和 `signature` 后计算；  
- `checksum = SHA-256(规范化字节)`，小写十六进制；  
- `signature = RSASSA-PSS(SHA-256, MGF1-SHA-256, saltLength=32)`，Base64；  
- RSA 密钥长度 2048 位及以上，推荐 3072 位；  
- LicenceData 和平台响应携带 `keyId`；平台维护公钥版本和重叠有效期，支持密钥轮换；  
- 平台响应和撤销/续期通知使用独立平台密钥，包含 `timestamp`、`nonce`、`requestId` 并签名，子应用校验时间窗和 nonce 防重放；  
- 提供跨语言测试向量，确保 Java、Go、Python 等实现一致。  

### D.9 模块控制覆盖范围

**问**：除 HTTP 接口外，定时任务、MQ 消费、批处理、WebSocket 等入口也必须拦截。  

**答**：已补充：  

- 拦截范围覆盖 HTTP Controller、定时任务、MQ 消费者、批处理、WebSocket、内部 RPC、异步任务、文件导入导出、缓存刷新任务等所有入口；  
- 默认 fail-closed，未标注或未分类的入口视为未授权；始终启用的基础功能必须显式声明为基础模块；  
- 验收增加非 HTTP 入口越权测试。

### D.11 License 与 HA／灾备／集群／迁移专项说明

**客户关切问题**：请说明 license 机制在高可用、灾备、集群部署及环境迁移场景下的适用方式、授权识别规则、许可占用与释放逻辑，以及客户业务连续性如何保障。

#### 设计依据

- **一机一 Licence 强绑定原则**：方案以 `appCode` 作为子应用（租户）唯一标识，以 `machineCode`（机器码）作为运行实例唯一标识，每份 Licence 仅绑定一台机器、仅允许该机器激活，以此精确识别超范围部署并支持平台统一审计与撤销。
- **运行期去中心化（无心跳）原则**：子应用本身已接入集成平台，首次激活与启动状态查询复用平台既有体系，而运行期授权判定完全由子应用在本地通过内存缓存完成，不设心跳机制，彻底消除集成平台或网络抖动对医院核心业务运行期的耦合依赖。

#### 实现方式

1. **高可用（HA）／灾备／集群／迁移的适用方式**：

- **HA／集群／灾备多节点部署**：多台机器（物理机、虚拟机、云主机或 K8s 宿主机节点）部署同一子应用时，按各节点的 `machineCode` 分别签发独立的 `licence.json` 并导入集成平台。平台以 `(appCode, machineCode)` 二元组作为唯一键定位每个实例的唯一有效 Licence，同一应用下不同机器码的授权状态独立维护、互不干扰。
- **灾备／冷备节点“初验预激活”机制**：针对主备 HA（含冷备/温备）及异地灾备节点，在项目部署上线及初验阶段，必须将所有主备及灾备节点全部启动并连入集成平台完成一次“首次联网激活”，确保每台备机本地均已持久化生成合法的 `licence.txt`。当发生机房级灾难（即便此时集成平台不可达）拉起备机时，备机可直接读取本地 `licence.txt` 验签完成离线启动，保障灾备切换零阻断。
- **环境迁移处理方式**：跨物理机或跨宿主机环境迁移导致底层硬件改变时，`machineCode` 发生变更，系统将其识别为新实例。采用“**先在新环境导入新机器码 Licence 并完成激活 → 切换业务流量 → 在平台撤销旧机器码 Licence**”的平滑迁移方式，实现业务零中断迁移。

2. **授权识别规则**：

- **硬件特征固定优先级采集**：子应用在运行时实时读取底层不可变硬件特征（严禁通过环境变量或启动参数注入机器码）：首选 **P1 SMBIOS 整机 UUID**（`/sys/class/dmi/id/product_uuid`），次选 **P2 SMBIOS 主板序列号**（`/sys/class/dmi/id/board_serial`），兜底选择 **P3 主系统盘固件序列号 + CPU ID**（遍历 `/dev/disk/by-id`，剔除 `usb-*`、`dm-*`、`loop-*`、`md-*` 及分区链接 `*-part*`，仅取系统根分区所在物理磁盘），高安全物理机可选 **TPM 2.0 背书密钥（EK 公钥指纹）模式**。
- **标准化 SHA-256 摘要生成**：剔除 `unknown`、`default string`、`none`、全 `0`/全 `F` 等无效占位符后，去除首尾空白并转为大写，添加来源前缀（`UUID:` / `BOARD:` / `DISK:` / `TPM:`）后计算 64 位小写十六进制 SHA-256 摘要作为 `machineCode`。
- **二元组强身份校验**：每次请求均须携带 `appCode + machineCode`，平台强制校验 `appCode` 与请求凭据绑定的应用一致，防止跨应用越权读取。

3. **许可占用与释放逻辑**：

- **占用与幂等**：同一 `(appCode, machineCode)` 同时仅存一份有效 Licence；子应用本地验签通过后调用平台激活接口完成占用；激活接口幂等，同一机器重复激活返回相同结果。
- **无数量配额**：方案移除 `maxUsers` 限制，模块仅控制启用状态与有效期，不设并发或用户配额。
- **释放与版本替代**：同机续期时通过更高 `revision`（单调递增）及 `supersedesLicenceId` 导入新 LicenceData 自动替代旧版；机器下线或迁移后，管理员在平台对该 `(appCode, machineCode)` 执行撤销（`REVOKE`）释放许可并留存审计记录。

4. **客户业务连续性保障机制**：

- **运行期零外部访问**：启动成功后 Licence 状态载入内存缓存，所有业务接口拦截只读内存缓存，不访问集成平台或本地文件。
- **重启期断网降级兜底**：已有本地 `licence.txt` 的子应用重启时优先联网查询平台；若遇网络故障、超时或平台不可用（5xx），自动降级读取本地 `licence.txt` 验签启动，杜绝因平台短暂故障导致子应用批量无法重启。
- **模块级故障隔离**：单个模块过期或被平台暂停，仅拦截该模块入口（返回 403），不影响整个子应用及其他已授权模块正常运行。

#### 适用边界

- 本方案适用于物理机、虚拟机（VMware/KVM 等）、云主机（ECS/CVM 等）及容器化（Docker/K8s）下的单机、主备 HA、多节点集群及灾备部署。
- 首次激活必须与院内集成平台网络连通；未完成首次激活（本地无有效 `licence.txt`）的全新节点无法在集成平台失联状态下直接离线启动。

#### 责任安排

- **我方（平台与子应用研发方）**：负责提供符合幂等激活、二元组隔离、内存级拦截及断网重启降级规范的集成平台、子应用客户端及宿主机独立机器码采集工具；针对核心医院客户支持预签发冷备机授权，并在收到换机申请与有效机器码后提供应急签发支持。
- **实施与客户方**：在 VMware/KVM 等虚拟化环境通过模板克隆多台集群/HA 虚拟机时，必须在虚拟化管理平台勾选“**生成新的 BIOS UUID / 实例 UUID**”，防止克隆机 `product_uuid` 相同引发机器码冲突；非 root 用户运行环境下需在服务器初始化时执行 `sudo chmod 0444 /sys/class/dmi/id/product_uuid /sys/class/dmi/id/board_serial` 赋予只读权限；上线初验时须配合完成全部主备/灾备节点的首次联网预激活。

### D.12 隔离网／离线模式与撤销时效专项说明

**客户关切问题**：请说明隔离网络及离线部署模式下的授权激活、校验、续期与撤销机制；明确撤销在离线场景下的生效时效、边界条件及相应的风险控制措施。

#### 设计依据

- **离线私钥签名与三重数据验签原则**：签名私钥仅在离线签名环境（`keygen.jar` / HSM）中保存，绝不进入医院现场环境；平台和子应用仅持有公钥。平台数据、本地 `licence.txt` 和内存缓存均必须来自经 RFC 8785 + RSASSA-PSS-SHA256 验签通过的 LicenceData 或平台签名通知。
- **安全边界单向收紧原则**：平台只能撤销 Licence、暂停已授权模块或下发更高 `revision` 的新签名 LicenceData，不能增加签名之外的模块，也不能延长签名有效期。

#### 实现方式

1. **两层“隔离网／离线模式”场景界定与激活、校验、续期机制**：

- **场景 A：医院外网隔离、院内网连通（标准医院内网场景）**

  - **离线签发与导入**：现场通过采集工具或启动自检日志获取 `machineCode`；我方在离线环境使用 `keygen.jar` 生成签名的 `licence.json`，通过安全介质摆渡至医院内网，粘贴/上传至院内集成平台完成验签登记。

    - **院内激活与校验**：子应用通过院内网络请求院内集成平台获取授权码与公钥（支持通过 `--licence-public-key` 启动参数固定公钥防平台被攻破伪造），本地验签后激活并生成 `licence.txt` 及内存缓存。
    - **院内续期**：导入更高 `revision` 的新 `licence.json` 至院内集成平台，通过 SSE `RENEW` 事件实时热更新子应用本地文件与内存缓存，或在下次重启查询时自动更新。
- **场景 B：子应用与院内集成平台通信中断或深度隔离网段（离线运行场景）**

  - **离线校验与重启**：子应用一旦完成首次激活生成本地 `licence.txt`（内含 `licenceCode`、`licencePublicKey`、`platformPublicKey`、`keyId` 等），在后续与院内集成平台网络中断期间，运行期直接读内存缓存校验，重启时自动读取本地 `licence.txt` 并按本地保存的 `keyId` 对应公钥完成离线验签启动。

    - **特殊深度隔离网段工程激活**：若子应用部署在初期施工未通网或院内特殊隔离网段，实施时可通过临时开通至院内集成平台的单次激活网络白名单完成首次激活落盘 `licence.txt`，随后即可关闭网络长期离线运行（如确需完全无平台网络的纯单机文件导入激活，可通过第十一章【可选 SDK 方案】扩展离线激活包工具支持）。

2. **撤销机制与离线场景下的生效时效、边界条件**：

- **在线场景撤销时效（秒级生效）**：当 SSE 连接正常时，管理员在平台执行撤销，平台立即推送 `REVOKE` 通知；子应用收到后**先将内存缓存置为 `REVOKED`（毫秒级立即阻断所有业务入口），再原子改写本地 `licence.txt`**，并通过 HTTPS 接口回传确认（平台默认确认超时阈值为 **30 秒**）。
- **离线场景撤销生效时效与边界条件（已知残余风险）**：由于方案不设运行期心跳且禁止轮询，若管理员在平台发起撤销时目标子应用正处于离线/断网状态，则在**子应用恢复网络连接收到 SSE 补发通知、或下次联网启动调用状态查询接口之前**，该离线实例仍会按内存缓存中的既有状态继续运行（最长不超过原签名 LicenceData 的 `expiryDate` 自然到期日）。此为无心跳高可用架构下的已知残余风险与明确边界。

3. **离线撤销场景的五重风险控制与补偿措施**：

- **措施 1（未确认强告警与状态高亮）**：平台未收到 `memoryUpdated=true` 且 `fileUpdated=true` 确认前，状态严禁置为完成，而是标记为 `REVOKE_PENDING` 或 `REVOKE_FAILED`，在管理页顶部汇总与明细页高亮展示，触发**高（High）级别告警**，并按退避策略重发同一 `noticeId`。
- **措施 2（内存优先阻断）**：子应用处理撤销时强制先改内存为 `REVOKED` 再写磁盘；即便磁盘写入失败导致平台显示“撤销失败”，子应用运行期内存已实际完成业务阻断。
- **措施 3（7 天断点续传与重连强制校准）**：平台默认保留 7 天未确认通知；网络恢复重连 SSE 时按 `Last-Event-ID` 自动补发，或通过 `stream-ready` / `replay-required` 事件强制触发 HTTPS 状态查询对齐撤销状态。
- **措施 4（联网重启一票否决）**：子应用重启只要网络可达即优先查询平台；一旦平台返回 `REVOKED`，立即同步覆写本地 `licence.txt`（写入平台签名的 `revocationNotice`）和内存缓存并阻断启动，**严禁在平台明确返回撤销时降级使用本地文件**。
- **措施 5（签名有效期与防时间回拨硬边界）**：离线实例受 RSA 签名保护的 `expiryDate` 强制约束，且子应用校验系统时间不得早于 `issuedAt` 及本地 `lastSyncAt`，防止通过离线回拨系统时间规避到期。

#### 适用边界

- 在线实时撤销适用于子应用与院内集成平台保持 HTTPS/SSE 连通的场景（生效时效 < 30 秒）。
- 离线实例的撤销指令将在网络恢复重连或下次联网重启时完成最终一致性补偿生效。

#### 责任安排

- **我方**：负责实现平台撤销状态追踪（`REVOKE_PENDING`/`REVOKE_FAILED`）、高级别告警、7 天通知保留补发及子应用“先内存阻断、后原子写文件”的防篡改逻辑。
- **实施与客户方**：对于院内长期离线网段机器，若发生合同终止或授权撤销，现场运维应配合网络恢复校准或现场清理下线对应实例。

### D.13 SSE 及网络前置条件和替代路径专项说明

**客户关切问题**：请明确方案对 SSE 及网络连通性的前置要求、依赖关系与故障影响；如前置条件不满足或链路不可用，请说明可行的替代路径及其限制。

#### 设计依据

- **轻量化单向通道原则**：授权状态变更（撤销、续期、模块暂停/恢复）仅需平台向子应用单向推送，采用基于标准 HTTP/HTTPS 的 **SSE（Server-Sent Events）单向推送 + 独立 HTTPS POST 确认**架构，可直接复用现有网关、TLS 和鉴权体系，避免引入消息队列（MQ）或 WebSocket 带来的额外中间件部署、专网端口开通与运维负担。

#### 实现方式

1. **SSE 及网络连通性的前置要求与依赖关系**：

- **协议与方向**：子应用需能通过标准 HTTPS 单向访问集成平台的 4 个短连接接口（`activation-info`、`activate`、`status`、`notices/{noticeId}/ack`）及 1 个 SSE 长连接端点（`GET /api/platform/app-licence/notices/stream`）。
- **凭据与参数复用**：直接复用子应用既有的平台接入地址与应用级鉴权凭据（`Authorization: Bearer <凭据>`），每次请求必带 `appCode + machineCode`。
- **网关与反向代理要求**：院内网关/Nginx 对 SSE 路径需支持 `Content-Type: text/event-stream; charset=utf-8`、`Cache-Control: no-cache`、`Connection: keep-alive`，并配置响应头 `X-Accel-Buffering: no` 禁用代理缓冲。
- **保活与超时重连参数**：平台每 **15 秒**发送一次 `: ping` 注释帧保活；子应用连续 **60 秒**未收到任何数据即判定连接失效，按 `1s、2s、4s、8s、16s、30s、60s`（封顶）指数退避加随机抖动自动重连。平台多实例部署时由平台内部通过粘性路由、共享连接注册表或内部转发投递通知，子应用客户端无感知。

2. **SSE 链路故障影响评估**：

- **对医院子应用业务运行：零影响**。SSE 断线或建连失败绝不等于 Licence 失效；断线期间子应用严格按内存缓存继续运行，**严禁因 SSE 通道断开而阻断正常业务**（仅当内存缓存已处于 `REVOKED` 时才维持阻断）。
- **对平台管控操作：实时性降级并告警**。断线期间平台下发的撤销/续期/模块暂停通知无法实时送达，平台将该实例标记为 `DISCONNECTED` 并在页面展示“通知未送达/待确认”及触发告警。

3. **前置条件不满足或链路不可用时的三级替代（补偿）路径及其限制**：

- **替代路径一：网络闪断下的 `Last-Event-ID` 自动断点续传**

  - **实现**：网络恢复后子应用重连 SSE 时携带请求头 `Last-Event-ID`，平台按序补发 7 天保留期内未确认的通知，子应用按 `noticeId` 幂等处理。

    - **限制**：要求断线时长不超过平台通知保留期（默认 7 天）。
- **替代路径二：超出保留期或状态失步下的 `stream-ready` / `replay-required` 触发式 HTTPS 拉取**

  - **实现**：重连成功瞬间平台下发 `stream-ready`（含 `currentRevision`、`status`、`lastNoticeId`），子应用与本地内存比对不一致（或收到平台因超 7 天保留期下发的 `replay-required`）时，立即主动调用短连接接口 `POST /api/platform/app-licence/status` 拉取最新状态与新 LicenceData 完成对齐。

    - **限制**：需网关允许 SSE 完成初始连接握手。
- **替代路径三：安全网关彻底阻断 SSE 流时的“标准 HTTPS 短连接状态查询”替代路径**

  - **实现**：若医院特定网段防火墙或旧版代理彻底阻断 `text/event-stream` 长连接，由于 `POST /api/platform/app-licence/status` 为普通 HTTPS POST 短连接接口，完全不受 SSE 阻断影响，可通过两种方式完成状态同步：

    1. **免重启按需触发同步（推荐）**：在子应用管理后台（或本地运维端点）提供“**手动同步授权状态**”按钮，管理员在平台导入续期 Licence 或变更状态后，点击同步即可按需调用一次 `POST /api/platform/app-licence/status` 拉取最新 LicenceData 并热更新内存缓存与 `licence.txt`，**无需重启子应用进程**；
    2. **随常规维护重启自动同步**：子应用在每次重启时均会自动调用 `POST /api/platform/app-licence/status` 完成最新续期或撤销状态补偿对齐。

    - **限制**：在彻底不支持 SSE 的网络环境下，平台管控指令无法由平台端自动秒级推入子应用，需配合管理员点击一次“同步授权状态”或待子应用重启时生效。

#### 适用边界

- 标准模式下要求院内反向代理支持 HTTP/1.1 keep-alive 并关闭针对 `/api/platform/app-licence/notices/stream` 的响应缓冲（`X-Accel-Buffering: no`）。
- 严禁子应用通过后台高频定时轮询替代 SSE，以免对集成平台造成不必要的并发压力。

#### 责任安排

- **我方**：负责在平台侧输出 `X-Accel-Buffering: no` 响应头、15 秒保活帧、7 天通知保留队列，并在子应用侧实现指数退避重连、幂等处理及按需触发 `status` 查询能力。
- **实施与客户方**：负责在医院内网 Nginx/网关或防火墙策略中放行子应用至集成平台的 HTTPS 访问，并按实施手册为 SSE 路径配置关闭代理缓冲。

### D.14 容器部署兼容性与单节点多 Pod 防冲突专项说明

**客户关切问题**：请说明方案对容器化部署及相关运行形态的兼容性，包括授权绑定、弹性伸缩、实例重建、节点替换等场景下的处理方式。

#### 设计依据

- **“算法完全统一、容器穿透底层”原则**：容器默认隔离宿主机硬件视图（容器内直接读取主板序列号常为 `unknown`，虚拟网卡 MAC 随容器重建漂移）。因此方案通过将宿主机真实硬件标识目录以**只读（`ro`）**方式挂载至容器内，使容器内进程穿透隔离层读取宿主机工作节点（Worker Node）底层硬件特征，执行与物理机完全一致的 SHA-256 机器码生成算法，且**无需开启容器 `privileged` 特权模式**，完全符合企业与医院 K8s 安全基线。

#### 实现方式

1. **容器化授权绑定标准配置**：

- **只读挂载宿主机硬件目录**：在 Docker Compose 或 K8s Deployment 中，必选只读挂载 `/sys/class/dmi/id:/sys/class/dmi/id:ro`（对应 P1 `product_uuid`、P2 `board_serial`）及 `/dev/disk/by-id:/dev/disk/by-id:ro`（对应 P3 磁盘兜底）。容器内即便拥有 `root` 权限也无法篡改只读挂载源。
- **本地授权文件节点级持久化**：挂载宿主机本地路径（如 K8s `hostPath` `type: FileOrCreate` 挂载 `/data/sub-app/licence.txt` 至 `/app/licence.txt`，或挂载目录并通过 `--licence-cache=/app/data/licence.txt` 指定）以持久化保存激活后的本地文件。

2. **容器相关运行形态的具体处理方式**：

- **场景 1：实例重建（Pod 崩溃重启、销毁重建、应用镜像版本升级）**

  - **处理方式**：通过 K8s 节点亲和性调度将 Pod 固定在已获授权的宿主机节点，并通过 `hostPath` 持久化 `/app/licence.txt`。Pod 重建后宿主机 `machineCode` 不变且本地 `licence.txt` 仍在，启动时联网查询平台（或离线读本地文件）即可秒级恢复；即便本地文件被清理，因平台激活接口对同一 `(appCode, machineCode)` 幂等，Pod 也会自动重新完成激活。
- **场景 2：K8s 节点级高可用容灾与弹性伸缩（多副本扩容 / 节点故障漂移）**

  - **多节点授权池（Node Pool）容灾机制**：为兼顾“一机一 Licence”强绑定与 K8s 节点宕机时的 Pod 自动漂移自愈能力，生产环境可将 $N$ 台（如 2~3 台）K8s Worker 节点规划为该子应用的“授权节点池”，预先采集这 $N$ 台宿主机的 `machineCode` 并分别签发导入 Licence。在 Deployment 中配置 `nodeAffinity`（`In: [worker-node-01, worker-node-02, ...]`），允许 Pod 在已授权节点池内自由故障漂移或按授权节点数横向扩容副本。

    - **存储隔离红线（严禁跨节点共享 `licence.txt`）**：由于每台宿主机生成的 `licence.txt` 绑定了该宿主机特定的 `machineCode`，`/app/licence.txt` **必须使用宿主机本地存储（`hostPath` 或 Local PV）**，**严禁使用 NFS/NAS/CephFS 等跨节点共享 PVC 挂载 `/app/licence.txt`**，防止不同宿主机上的 Pod 读写同一份文件引发机器码不匹配（`INVALID`）阻断。
    - **单节点单 Pod 调度防写冲突约束（Pod 反亲和性，关键红线）**：
      - **并发写冲突风险**：在多副本扩容（HPA 或手动伸缩）场景下，若同一子应用的多个 Pod 副本被调度至**同一个 Worker 宿主机节点**，且均通过 `hostPath` 挂载同一本地文件 `/data/sub-app/licence.txt`，在激活、续期或撤销（原子改写落盘）时会产生**多进程并发写冲突（Race Condition）**甚至损坏文件。
      - **落地处置规范（二选一）**：
        1. **推荐规范（强制 Pod 强反亲和性调度）**：在 Deployment 中配置 `podAntiAffinity`（`topologyKey: kubernetes.io/hostname`），强制**同一子应用在同一个 Worker 宿主机节点上严格至多运行 1 个 Pod 副本**，多副本水平伸缩必须分散调度至授权节点池内的不同宿主机节点；
        2. **备选规范（按 Pod 独立隔离目录）**：若确需在单宿主机节点运行多个 Pod 副本，宿主机挂载目录需按 Pod 命名隔离（如通过 Kubernetes Downward API 将 Pod 名称作为子路径 `--licence-cache=/data/sub-app/$(POD_NAME)/licence.txt`），严禁多副本共用同一个本地文件。
- **场景 3：节点替换（K8s Worker 节点硬件淘汰、云主机宿主机更换）**

  - **处理方式**：宿主机更换导致 `machineCode` 变化，视为新实例。先在新 Worker 节点运行采集工具获取新 `machineCode`，签发新 `licence.json` 导入平台，随后将新节点加入 `nodeSelector` / `nodeAffinity` 标签完成 Pod 滚动重建与新节点在线激活，最后在平台撤销已下线的旧 Worker 节点 Licence。

#### 适用边界

- 支持 Docker、Docker Compose、Kubernetes（K8s）及基于 K8s 的国产信创容器云平台。
- 受 Licence 管控的子应用 Pod 必须在已登记 Licence 的宿主机节点（或授权节点池）内调度运行；不支持向未登记 Licence 的随机节点进行无状态弹性调度，也不支持无宿主机硬件目录挂载权限的 Serverless（如纯虚拟节点 Virtual Kubelet）形态。

#### 责任安排

- **我方**：提供标准 Docker Compose 与 K8s Deployment YAML 模板、宿主机独立采集工具及容器内非特权硬件特征读取能力。
- **实施与客户方**：负责按规范在宿主机初始化时对 DMI 文件执行 `chmod 0444`（当容器以非 root 运行时）；使用 Docker 单文件 bind mount 时须预先在宿主机创建空文件 `./data/licence.txt`（或改用目录挂载）以防 Docker 自动创建同名目录导致读写失败；配置 K8s 节点亲和性（`nodeAffinity`）、单节点单 Pod 反亲和性（`podAntiAffinity`）及 `hostPath` 本地持久化隔离。

### D.15 换机、紧急恢复、离线激活／续期与审计留痕专项说明

**客户关切问题**：请说明换机、硬件故障后的紧急恢复、离线激活与续期的标准流程、审计留痕办法。

#### 设计依据

- **硬件特征抗干扰与激活幂等设计**：机器码采集优先锚定主板 BIOS UUID（P1）与主板序列号（P2），P3 磁盘采集仅取系统根分区物理盘并剔除移动盘与逻辑卷，且完全不使用网卡 MAC，从根源上保证常规硬件维护不触发机器码变动；同时平台激活接口设计为幂等，支撑系统重装后的零人工自动恢复。
- **全链路双向可追溯原则**：平台侧与子应用侧分别记录完整的生命周期管理审计与运行拦截日志，且所有通信与通知均带签名、时间戳与 `nonce`，确保任何授权变更均有据可查、不可抵赖。

#### 实现方式

1. **换机与硬件故障后的三级紧急恢复机制**：

- **第一级：常规外设/存储/网卡更换（免恢复，零感知）**：更换故障网卡、扩容挂载数据盘、插拔 USB 设备、调整 LVM 逻辑卷或更换非主板配件时，`product_uuid` / `board_serial` 不变，`machineCode` 100% 稳定，子应用无需任何恢复操作即可正常运行。
- **第二级：系统盘损坏重装或容器卷误删（主板未换，自动幂等快速恢复）**：若硬盘损坏重装操作系统导致本地 `licence.txt` 丢失，由于主板未换，`machineCode` 保持不变；子应用启动联网后自动调用平台 `activation-info` 和 `activate` 接口，平台按同一 `(appCode, machineCode)` 幂等规则直接下发原授权码并激活，自动重建 `licence.txt`，无需重新签发 Licence。
- **第三级：主板烧毁或整机宕机切换新机（`machineCode` 改变，应急恢复）**：

  - **方式 A（切换至已预激活备机）**：直接切换至初验时已完成预激活的 HA 备机或预置授权冷备节点，业务即刻恢复。

    - **方式 B（切换至全新未登记服务器，应急签发恢复）**：在新服务器启动子应用，从控制台/错误日志直接复制自检打印的本机 `machineCode`（或运行宿主机采集工具），向我方提交应急签发申请生成新 `licence.json` 导入院内集成平台，重启子应用完成激活，随后在平台撤销故障旧机 Licence。

2. **离线生成与院内激活／续期标准机制**：

- **激活机制**：由离线环境 `keygen.jar` 生成 `licence.json` 导入院内集成平台；子应用首次启动通过院内网络拉取授权码、本地验签并调用激活接口后落盘 `licence.txt`。
- **续期机制**：使用 `keygen.jar` 指定递增的 `--revision` 与 `--supersedes` 生成新 `licence.json` 导入院内平台；在线实例通过 SSE `RENEW` 事件自动完成“先原子写 `licence.txt`、再切换内存缓存”的无感热续期；离线或无 SSE 实例在点击“同步授权状态”或下次联网重启时自动拉取更新。

3. **全方位审计留痕办法**：

- **集成平台侧集中审计**：

  - **登记与绑定记录**：完整保存 `LicenceData` 原始 JSON 字节（不重序列化）、`appCode`、`machineCode`、`licenceId`、`revision`、有效期、模块清单、验签结果及导入操作人。

    - **生命周期操作审计**：记录首次激活时间、撤销记录（含操作人、时间、`reason`）、续期版本替代链（`supersedesLicenceId`）、模块暂停/恢复操作人及时间。
    - **运行与通知落地审计**：记录每个实例最近状态查询时间、SSE 连接状态、通知发送时间（`noticeId`）、子应用确认时间（`appliedAt`）以及 `memoryUpdated` 和 `fileUpdated` 双项确认结果与失败原因。
- **子应用客户端侧本地审计**：

  - 记录本地验签失败、机器码采集降级/异常、首次激活失败、启动状态查询失败、SSE 建连/重连/补发/确认失败、本地文件写入失败及未授权/过期/暂停模块拦截（HTTP 403 及非 HTTP 入口拦截）日志与指标。

    - **安全脱敏约束**：`licence.txt` 严格限制为运行用户可读写（Windows 设同等 ACL），日志中严禁打印完整 `LicenceData` 或授权码原文。

#### 适用边界

- 自动幂等恢复适用于宿主机主板（`product_uuid` / `board_serial`）未发生改变的场景。
- 整机或主板更换必须走换机重签流程，旧机 Licence 撤销后不可逆，若需恢复必须签发更高 `revision` 的新 Licence。

#### 责任安排

- **我方**：在收到正式换机申请与有效机器码后提供应急换机 Licence 签发技术支持，保障平台与子应用审计日志完整准确。
- **实施与客户方**：发生硬件主板更换或整机迁移时，现场运维负责提供新机 `machineCode` 并在新机激活后配合在平台执行旧机 Licence 撤销确认。
